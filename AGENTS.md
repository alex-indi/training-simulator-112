# AGENTS.md

## Проект

Название проекта и приложения: «Учебный тренажер 112».

Технический идентификатор проекта и задач: `UT112`.

## Назначение

«Учебный тренажер 112» предназначен для обучения диспетчеров ДДС работе
с карточками происшествий, поступающими из Системы-112.

Точный бизнес-процесс ДДС пока уточняется. Текущие представления о предметной
области нельзя считать окончательными без подтверждения заказчика.

## Обязательное чтение

Перед изменением кода прочитать:

- `docs/product.md`;
- `docs/domain.md`;
- `docs/architecture.md`;
- `docs/code-style.md`;
- `docs/current-state.md`.

Если работа касается состояний или переходов карточки, дополнительно прочитать:

- `docs/state-machines.md`;
- `docs/questions/customer-questions.md`.

При создании перечисленных документов допускается работать до появления
остальных файлов.

## Материалы заказчика

Исходные документы заказчика не входят в обязательное чтение для каждой задачи.

При явном запросе на проверку требований по исходным материалам используй
`$customer-materials`. Загружай только источники, относящиеся к текущему вопросу.

## Источники истины

Использовать следующий порядок:

1. подтверждённые требования заказчика;
2. принятые ADR в `docs/decisions/`;
3. `docs/domain.md`;
4. `docs/architecture.md`;
5. описание текущей задачи WEEEK;
6. существующий код.

Если источники противоречат друг другу, не выбирать трактовку самостоятельно.
Зафиксировать противоречие и запросить решение.

## Статусы предметных знаний

В документации используются обозначения:

- `CONFIRMED` — подтверждено материалами или заказчиком;
- `ASSUMPTION` — рабочая гипотеза;
- `OPEN` — вопрос без ответа.

Не превращать `ASSUMPTION` или `OPEN` в бизнес-правило без отдельного решения.

При обнаружении нового открытого вопроса добавить его в
`docs/questions/customer-questions.md` или предложить такое изменение.

## Основные архитектурные правила

1. Backend является единственным источником бизнес-правил.
2. Frontend не определяет допустимые переходы состояний.
3. Backend возвращает frontend список `available_actions`.
4. Вся внешняя информация валидируется на границе backend.
5. Бизнес-логика переходов карточки хранится в одном backend-модуле.
6. Изменения состояния и запись истории выполняются атомарно.
7. Сервер является источником времени для оценки и журнала действий.
8. AI не является источником истины для детерминированной оценки.
9. AI, телефония и Virtual112 подключаются через изолированные модули
   или адаптеры.
10. Не добавлять новую инфраструктуру или абстракции без текущей необходимости.
11. Не создавать микросервисы, Redis, очереди или новые фреймворки без
    принятого архитектурного решения.

## Правила реализации

- Писать простой и явно читаемый код без неочевидной магии.
- Использовать полные и понятные имена без необязательных сокращений.
- Не выполнять несвязанный рефакторинг.
- Не изменять соседние модули без необходимости для текущей задачи.
- Не добавлять зависимости без обоснования.
- Не оставлять временный код, отладочные `print` и `console.log`.
- Не хранить секреты, токены, пароли и персональные данные в репозитории.
- Комментарии должны объяснять неочевидную логику или причину решения.
- Очевидный код не комментировать.
- Python-функции и методы документировать Google-style docstrings на русском.
- Следовать полным правилам из `docs/code-style.md`.

## API

- Использовать REST.
- В JSON использовать `snake_case`.
- Backend независимо проверяет права доступа и входные данные.
- Domain- и service-слои не должны зависеть от HTTP-кодов.
- События Socket.IO именовать в формате `domain.event`.
- Время хранить в UTC и передавать в ISO 8601.

## Тестирование

- Каждое изменение backend-бизнес-логики должно сопровождаться тестами.
- Каждый исправленный баг должен сопровождаться regression-тестом.
- Проверять разрешённые и запрещённые переходы состояний.
- Не добавлять snapshot-тесты.
- UI-тесты писать для критических пользовательских сценариев,
  а не для формального покрытия.

## Работа с задачей

Одна задача WEEEK соответствует одной Git-ветке.

Перед реализацией:

1. прочитать задачу и критерии приёмки;
2. проверить зависимости задачи;
3. прочитать связанную документацию;
4. изучить затрагиваемый код;
5. сформулировать короткий план;
6. убедиться, что изменение укладывается в границы задачи.

Если требования задачи недостаточны для безопасной реализации, не придумывать
бизнес-логику. Зафиксировать вопрос или блокирующее условие.

## Git

Формат ветки:

```text
feature/UT112-xxx-short-slug
fix/UT112-xxx-short-slug
refactor/UT112-xxx-short-slug
test/UT112-xxx-short-slug
docs/UT112-xxx-short-slug
chore/UT112-xxx-short-slug
```

Формат коммита:

```text
<type>(UT112-xxx): <описание на русском>
```

Разрешённые основные типы:

```text
feat
fix
refactor
test
docs
chore
build
ci
perf
revert
```

Название Pull Request:

```text
[UT112-xxx] Краткое описание
```

Правила:

- прямой push в `main` запрещён;
- изменения попадают в `main` только через Pull Request;
- способ слияния — squash merge;
- один коммит должен представлять один логический шаг;
- не смешивать несколько задач в одной ветке или Pull Request.

## Архитектурные изменения

Если задача требует изменить архитектуру, публичный API, модель данных,
границы модулей или ключевой бизнес-процесс:

1. остановить зависимую реализацию;
2. описать причину и последствия;
3. создать или обновить ADR;
4. актуализировать связанную документацию;
5. продолжить после принятия решения.

Небольшие локальные изменения, не меняющие архитектурные границы, отдельного
ADR не требуют.

## Перед завершением задачи

1. выполнить относящиеся к изменению проверки;
2. убедиться, что тесты проходят;
3. проверить итоговый diff;
4. удалить временный код;
5. обновить документацию при изменении поведения;
6. обновить `docs/current-state.md`, если изменилось фактическое состояние проекта;
7. сопоставить результат с критериями приёмки WEEEK-задачи;
8. указать выполненные проверки и известные ограничения в Pull Request.

Нельзя объявлять задачу завершённой только потому, что код написан.
