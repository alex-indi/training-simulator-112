# AGENTS.md

## Проект

Проект: **«Учебный тренажер 112»**.  
Исторический идентификатор задач: **`UT112`**; для новых правок номер не обязателен.

Проект делают два разработчика на нескольких компьютерах.

Главное правило:

> Git хранит состояние проекта. Codex-чат можно потерять без потери работы.

Пользователь не обязан помнить названия skills или вручную вести служебные файлы. Если намерение понятно из обычной фразы, выполняй работу автоматически.

## Обычная работа

После основного этапа разработки ведём небольшие исправления и улучшения прямо в чате. WEEEK больше не используем: не ищи там задачи, не меняй исполнителей и статусы. Номер `UT112-XX` и файл `tasks/UT112-XX.md` нужны только для уже начатой работы, где они существуют, либо по явной просьбе пользователя.

Перед первой правкой проверь `git status --short --branch` и `git branch --show-current`. Для самостоятельного набора правок создай обычную отдельную ветку с понятным именем, например `codex/fix-card-preview`. Если подходящая ветка уже открыта для этой работы, продолжай в ней. Не смешивай изменения из разных чатов и не затрагивай чужие незавершённые правки. Если текущее дерево занято другой работой, используй отдельный worktree.

Если работаешь от чистой `main`, сначала выполни `git pull --ff-only`, затем создай ветку. После создания или переключения проверь `git branch --show-current`. На `main` файлы не меняй. Кратко сообщи пользователю ветку и приступай к работе.

После небольшого исправления достаточно относящейся к нему проверки: теста, линтера, сборки или ручного воспроизведения. Не запускай весь набор тестов после каждой мелкой правки. Перед **итоговым коммитом и push** проверь diff и выполни полный относящийся к изменению набор проверок. Если проверка невозможна или падает по внешней причине, сообщи об этом явно.

### «Сохрани состояние, продолжу на другом компьютере»

Проверь diff, запиши сделанное и один точный следующий шаг в краткий handoff, выполни доступные короткие проверки, затем создай промежуточный commit и push текущей ветки. Полный прогон требуется перед итоговым коммитом, а не для промежуточного checkpoint. Используй `$project-checkpoint`.

### «Продолжи текущую работу»

Определи текущую ветку, прочитай Git status/diff и последние commits, затем handoff, если он есть. Прочитай только нужные документы, кратко скажи, где остановились, и продолжай. Используй `$project-resume`.

### «Готово, проверь и отправь»

Сверь результат с запросом пользователя, проверь diff, убери временный код, обнови документацию при изменении поведения, выполни полный относящийся набор проверок, затем сделай итоговый commit и push. Сообщи результат проверок и адрес ветки или PR, если он создан.

## Git

Одна самостоятельная работа = одна ветка. Для новых веток используй `codex/<short-slug>`; существующие ветки с `UT112-XX` можно продолжать. Номер задачи в имени ветки и коммита больше не обязателен.

Правила:

- не работать напрямую в `main`;
- не переносить рабочую папку между устройствами вручную;
- переключение устройств — только через commit + push + pull;
- не использовать force-push без явной причины;
- не добавлять `.env`, токены или материалы заказчика в Git;
- не использовать `git add .`, если можно явно выбрать нужные файлы.

---

## Handoff

Handoff нужен при паузе, переносе работы между устройствами или длительном изменении. Используй существующий `tasks/UT112-XX.md` для старой задачи; для новой работы без номера можно создать краткий файл в `tasks/`, заменив `/` в имени ветки на `-`. Для мелких правок handoff не обязателен.

Пользователь не обязан редактировать его вручную.

Codex поддерживает в нём только:

- что делаем;
- что уже сделано;
- что осталось;
- проверки;
- блокеры;
- один точный следующий шаг;
- последний commit / push.

Не превращай handoff в журнал каждого действия.

## Предметная граница

Основной обучаемый — **диспетчер ДДС**.

Он получает готовую карточку, принимает решение о реагировании своей службы, взаимодействует с группой реагирования и сам меняет статусы карточки на основании полученной информации.

Для MVP:

- используется виртуальная группа реагирования;
- коммуникация с ней идёт через встроенный текстовый чат;
- чат имитирует оперативный канал связи;
- состояние виртуальной группы не меняет статус карточки автоматически.

Учебные сценарии в коде называются `TrainingScenario`.

При разработке сценариев, генератора и карточек используй [действующую модель MVP](docs/current-state.md) и [библиотеку шаблонов](docs/scenario-library-and-generator.md). [Scenario Engine](docs/scenario-engine.md) — legacy/internal, а [исторический проект подготовки](docs/instructor-preparation-workflow.md) не заменяет фактический UI. Обычный шаблон не программирует сообщения служб, timeline, универсальные действия ДДС или пользовательские критерии оценки; работу бригады 101 выполняет runtime backend.

## Архитектура

Нормативно-справочные, классификационные, объектные и методические данные для работы и демонстрации тренажёра должны восстанавливаться из версионированных seed/import-файлов репозитория. Runtime-история тренировок в seed не входит. Изменения схемы выполняются только через Alembic; каждый импорт должен быть идемпотентным и не удалять исчезнувшие записи автоматически.

### Имена миграций Alembic при параллельной работе

- Для каждой новой миграции добавляй время создания в UTC с точностью до секунды и случайный суффикс из шести шестнадцатеричных символов. Формат файла: `YYYYMMDD_HHMMSS_<6hex>_<short_slug>.py`; значение `revision` должно совпадать с префиксом `YYYYMMDD_HHMMSS_<6hex>`. Например: `20260925_092131_a1b2c3_add_user_groups.py` и `revision = "20260925_092131_a1b2c3"`.
- Перед созданием миграции проверь, что её `revision` уникален среди файлов репозитория; `down_revision` указывай на фактическую родительскую миграцию. Не меняй ID уже применённой миграции без плана обновления существующих БД.
- После объединения параллельных веток проверь `alembic heads`: для проекта должна остаться одна вершина. Если появились независимые вершины, согласуй цепочку или создай merge-миграцию Alembic; перед push проверь `alembic upgrade head` на чистой БД.

Ключевые правила:

- модульный монолит;
- FastAPI + React + PostgreSQL;
- backend — источник бизнес-правил;
- REST — каноническое состояние;
- Socket.IO — realtime-уведомления;
- серверное время — источник временных метрик;
- AI и телефония — через адаптеры;
- не добавлять сложную инфраструктуру «на будущее».

Подробности: `docs/architecture.md` и `docs/decisions/ADR-001-foundation.md`.
