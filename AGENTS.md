# AGENTS.md

## Проект

Название продукта: **«Учебный тренажер 112»**.  
Технический идентификатор задач: **`UT112`**.

Проект разрабатывают два человека на нескольких устройствах. Репозиторий Git является долговременной памятью проекта. Чат Codex считается временным рабочим контекстом и может быть потерян в любой момент.

## Главный принцип непрерывности

> Не восстанавливай проект из старого чата. Восстанавливай его из Git, документации, task handoff и WEEEK.

Ни одно важное решение, ограничение, открытый вопрос или незавершённый шаг не должен существовать только в диалоге с агентом.

## Автоматическое восстановление контекста

В начале новой сессии или после просьб вроде «продолжи», «восстанови задачу», «продолжай работу»:

1. определи корень Git-репозитория;
2. прочитай этот `AGENTS.md`;
3. прочитай `docs/current-state.md`;
4. определи текущую ветку и извлеки из неё `UT112-xxx`, если идентификатор присутствует;
5. если существует `tasks/UT112-xxx.md`, прочитай его;
6. прочитай только те доменные документы, которые нужны текущей задаче;
7. выполни `git status`, посмотри последние коммиты и незакоммиченный diff;
8. при доступном WEEEK MCP прочитай соответствующую задачу WEEEK;
9. кратко сформулируй: где остановились, что уже сделано, что осталось, есть ли блокеры;
10. продолжай с ближайшего незавершённого шага, не прося пользователя пересказывать предыдущий чат.

Для этого процесса используй skill `$project-resume`.

## Перед паузой, сменой устройства или завершением сессии

Если работа не завершена либо пользователь просит сохранить прогресс:

1. синхронизируй `tasks/UT112-xxx.md` с фактическим состоянием ветки;
2. зафиксируй выполненное, проверки, принятые локальные решения, блокеры и **один точный следующий шаг**;
3. если появилось долговременное решение — обнови подходящий документ или `docs/decision-log.md`;
4. проверь `git status` и diff;
5. при необходимости создай промежуточный checkpoint commit;
6. напомни о `git push`, если изменения ещё не отправлены в remote.

Для этого процесса используй skill `$project-checkpoint`.

## Источники истины

Используй такой приоритет:

1. прямой свежий ответ заказчика по конкретному вопросу;
2. профильные рабочие инструкции и материалы заказчика;
3. принятые ADR;
4. `docs/domain.md`;
5. `docs/product.md` и `docs/architecture.md`;
6. task handoff и WEEEK-задача;
7. существующий код.

Если источники противоречат друг другу, не устраняй противоречие догадкой. Зафиксируй его.

## Статусы знаний

- `CONFIRMED` — подтверждено заказчиком или материалами;
- `PRODUCT_DECISION` — принято командой для тренажера;
- `ASSUMPTION` — рабочая гипотеза;
- `OPEN` — подтверждённого ответа нет.

`PRODUCT_DECISION` нельзя представлять как реальный процесс ДДС.
`ASSUMPTION` и `OPEN` нельзя превращать в жёсткое правило без решения.

## Критическая предметная граница

### Оператор Службы-112

Формирует первичную карточку, работает с признаками происшествия, итоговым типом и списком оповещения.

### Диспетчер ДДС — основной обучаемый

Получает уже сформированную карточку, анализирует её, принимает решение о реагировании своей службы, организует взаимодействие с группой реагирования и ведёт статусы/комментарии своей службы.

Не смешивай эти роли.

## Текущая модель реагирования

`CONFIRMED`:

- после принятия карточки решение о реагировании принимает диспетчер, если у него есть полномочия, иначе руководство;
- старший группы реагирования сообщает в ДДС об обстановке и ходе работ либо диспетчер сам связывается со старшим;
- в реальности применяются телефон, радиостанция и внутренние каналы;
- для проекта заказчик разрешил ограничиться телефоном;
- внутренний процесс конкретных служб различается и не должен универсально воспроизводиться.

`PRODUCT_DECISION` для MVP:

- используется виртуальная группа реагирования;
- обучаемый назначает ей задачу;
- коммуникация имитируется встроенным онлайн-чатом как заменителем телефонного канала;
- виртуальная группа имеет собственное состояние и присылает сообщения о ходе работ;
- статус карточки ДДС **не меняется автоматически** вслед за состоянием виртуальной группы: обучаемый должен интерпретировать сообщение и сам выбрать корректный статус.

## Архитектурные правила

1. Модульный монолит.
2. Backend — единственный источник бизнес-правил.
3. Frontend получает `available_actions`, но не вычисляет workflow самостоятельно.
4. REST — канонический источник состояния.
5. Socket.IO — уведомления в реальном времени, а не хранилище состояния.
6. Серверное время — источник истины для метрик.
7. Значимые действия фиксируются как история событий/действий.
8. AI не является источником истины для детерминированных правил.
9. Телефония и AI подключаются через адаптеры.
10. Не добавлять микросервисы, Redis, Kafka, RabbitMQ, Celery, Kubernetes и похожую инфраструктуру без отдельного решения.
11. Не привязывать доменную модель к конкретному формату XLSX классификатора.
12. Не моделировать внутреннее устройство каждой ДДС: у служб оно различается.

## Git и несколько устройств

- Git remote — единственный способ переносить работу между устройствами.
- Не переносить рабочую папку ZIP-архивами, флешкой или ручным копированием.
- Одна WEEEK-задача = одна ветка.
- Перед сменой устройства незавершённую полезную работу можно коммитить checkpoint-коммитом и обязательно отправлять в remote.
- Прямой push в `main` запрещён.
- Merge — через Pull Request, предпочтительно squash merge.

Ветки:

```text
feature/UT112-xxx-short-slug
fix/UT112-xxx-short-slug
refactor/UT112-xxx-short-slug
test/UT112-xxx-short-slug
docs/UT112-xxx-short-slug
chore/UT112-xxx-short-slug
```

Коммиты:

```text
<type>(UT112-xxx): <описание на русском>
```

## Работа с task handoff

Файл `tasks/UT112-xxx.md` отражает состояние **конкретной ветки/задачи**.

Он должен содержать:

- цель;
- статус;
- что уже сделано;
- затронутые файлы;
- проверки;
- важные решения внутри задачи;
- блокеры;
- точный следующий шаг;
- последний checkpoint commit, если есть.

`docs/current-state.md` отражает состояние `main`, а не каждую незавершённую ветку.

## WEEEK

WEEEK хранит управленческое состояние задачи: backlog, исполнитель, приоритет, статус и критерии приёмки.

Git/task handoff хранит техническое состояние реализации.

Не переводить задачу в `Done` автоматически. Финальное завершение подтверждает человек.

## Материалы заказчика

Исходные материалы не коммитятся в публичный репозиторий. Для точечной проверки используй `$customer-materials`.

Не загружай весь набор документов в контекст одновременно.

## Код-стиль и тесты

Следуй `docs/code-style.md`.

Минимум:

- Python: type hints, понятные имена, Google-style docstrings на русском;
- JS: функциональные React-компоненты и hooks;
- backend business logic обязательно тестировать;
- исправление бага сопровождается regression test;
- snapshot tests не использовать;
- не выполнять несвязанный рефакторинг.

## Архитектурные изменения

Если новая информация требует изменения архитектуры, модели данных, публичного API или ключевого workflow:

```text
новая информация
→ CHANGE / needs-discussion
→ анализ влияния
→ ADR
→ обновление architecture.md/domain.md
→ обновление затронутых задач
→ реализация
```

## Перед объявлением задачи завершённой

1. выполнить относящиеся проверки;
2. проверить diff;
3. удалить временный код;
4. актуализировать task handoff;
5. обновить долгоживущие документы, если изменилось поведение;
6. сопоставить результат с критериями приёмки;
7. убедиться, что изменения закоммичены и доступны второму разработчику через remote.
