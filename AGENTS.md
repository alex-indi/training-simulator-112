# AGENTS.md

## Проект

Проект: **«Учебный тренажер 112»**.  
Идентификатор задач: **`UT112`**.

Проект делают два разработчика на нескольких компьютерах.

Главное правило:

> Git хранит состояние проекта. Codex-чат можно потерять без потери работы.

Пользователь не обязан помнить названия skills или вручную вести служебные файлы. Если намерение понятно из обычной фразы, выполняй нужный workflow автоматически.

## Четыре обычные команды пользователя

### «Начни задачу UT112-XX»

Это отдельный **start workflow**, а не resume.

Автоматически:

1. найди задачу в WEEEK;
2. проверь, что она не занята другим разработчиком;
3. назначь текущего пользователя, если исполнитель не задан;
4. переведи задачу из `К работе` в `В работе`;
5. проверь Git:
   ```bash
   git status --short --branch
   git branch --show-current
   ```
6. **до изменения файлов задачи обязательно создай или выбери отдельную ветку**;
7. если текущая ветка `main` и рабочее дерево чистое:
   ```bash
   git pull --ff-only
   git switch -c <type>/UT112-XX-short-slug
   ```
8. если подходящая ветка уже существует — переключись на неё вместо создания новой;
9. проверь результат:
   ```bash
   git branch --show-current
   ```
   Имя текущей ветки обязано содержать `UT112-XX`;
10. только после успешной проверки ветки создай `tasks/UT112-XX.md`;
11. прочитай только нужную документацию;
12. кратко сообщи имя ветки, план и начинай работу.

Если отдельную ветку создать/выбрать не удалось — **не начинай изменять файлы задачи**. Сначала сообщи пользователю причину.

Используй `$weeek-workflow` под капотом. `$project-resume` предназначен для продолжения уже начатой задачи, а не для её старта.

### «Сохрани состояние, продолжу на другом компьютере»

Автоматически:

1. проверь Git diff;
2. обнови `tasks/UT112-XX.md`;
3. запиши, что сделано и **один точный следующий шаг**;
4. выполни доступные короткие проверки;
5. создай безопасный commit;
6. push текущей ветки;
7. кратко сообщи, что состояние сохранено.

Используй `$project-checkpoint`.

### «Продолжи текущую задачу»

Автоматически:

1. определи текущую ветку и Task ID;
2. прочитай `tasks/UT112-XX.md`;
3. посмотри Git status, diff и последние commits;
4. при доступном WEEEK прочитай задачу;
5. прочитай только нужные документы;
6. кратко скажи, где остановились;
7. продолжай с записанного следующего шага.

Используй `$project-resume`.

### «Задача готова, проверь всё»

Автоматически:

1. сверь результат с задачей WEEEK;
2. запусти относящиеся проверки;
3. проверь diff;
4. убери временный код;
5. обнови документацию, если изменилось поведение;
6. обнови handoff;
7. commit/push, если это ещё не сделано;
8. сообщи пользователю результат проверки.

После явного подтверждения пользователя вроде **«всё работает, заверши задачу»** переведи её в `Готово`.

## WEEEK

Доска намеренно простая:

```text
К работе → В работе → Готово
```

Смысл:

- `К работе` — задачу можно брать;
- `В работе` — её делает один из разработчиков;
- `Готово` — результат проверен человеком.

Не создавать дополнительные обязательные стадии вроде Review, QA, Controller или Blocked.

Если задача заблокирована, оставь её в `В работе` и запиши причину в handoff/описание.

У каждой задачи один основной исполнитель.

## Git

### Обязательный Git-gate перед началом задачи

Перед первой правкой по новой задаче текущая ветка должна содержать её ID.

Например для `UT112-12` допустимо:

```text
feature/UT112-12-short-name
fix/UT112-12-short-name
docs/UT112-12-short-name
chore/UT112-12-short-name
```

Если `git branch --show-current` возвращает `main`, работать над задачей ещё нельзя.

После создания/переключения ветки всегда повторно выполнить:

```bash
git branch --show-current
```

и убедиться, что в имени есть нужный `UT112-XX`.

Одна задача = одна ветка.

Примеры:

```text
feature/UT112-12-short-name
fix/UT112-13-short-name
docs/UT112-14-short-name
```

Коммит:

```text
feat(UT112-12): добавить ...
fix(UT112-13): исправить ...
docs(UT112-14): уточнить ...
chore(UT112-12): сохранить промежуточное состояние
```

Правила:

- не работать напрямую в `main`;
- не переносить рабочую папку между устройствами вручную;
- переключение устройств — только через commit + push + pull;
- не использовать force-push без явной причины;
- не добавлять `.env`, токены или материалы заказчика в Git;
- не использовать `git add .`, если можно явно выбрать нужные файлы.

## Task handoff

`tasks/UT112-XX.md` — служебная память незавершённой задачи.

Пользователь не обязан редактировать его вручную.

Codex поддерживает в нём только:

- что делаем;
- что уже сделано;
- что осталось;
- проверки;
- блокеры;
- один точный следующий шаг;
- последний commit / push.

Не превращай handoff в журнал каждого действия.

## Предметная граница

Основной обучаемый — **диспетчер ДДС**.

Он получает готовую карточку, принимает решение о реагировании своей службы, взаимодействует с группой реагирования и сам меняет статусы карточки на основании полученной информации.

Для MVP:

- используется виртуальная группа реагирования;
- коммуникация с ней идёт через встроенный текстовый чат;
- чат имитирует оперативный канал связи;
- состояние виртуальной группы не меняет статус карточки автоматически.

Учебные сценарии в коде называются `TrainingScenario`.

При разработке сценариев, генератора и карточек используй [концепцию библиотеки](docs/scenario-library-and-generator.md) как источник требований и [концепцию Scenario Engine](docs/scenario-engine.md) как целевую модель исполнения.
При разработке функциональности, связанной с инцидентами, сценариями, карточками происшествий и генерацией учебных ситуаций, используй [docs/scenario-library-and-generator.md](docs/scenario-library-and-generator.md) как источник требований и архитектурных решений.

## Архитектура

Нормативно-справочные, классификационные, объектные и методические данные для работы и демонстрации тренажёра должны восстанавливаться из версионированных seed/import-файлов репозитория. Runtime-история тренировок в seed не входит. Изменения схемы выполняются только через Alembic; каждый импорт должен быть идемпотентным и не удалять исчезнувшие записи автоматически.

### Имена миграций Alembic при параллельной работе

- Для каждой новой миграции добавляй время создания в UTC с точностью до секунды и случайный суффикс из шести шестнадцатеричных символов. Формат файла: `YYYYMMDD_HHMMSS_<6hex>_<short_slug>.py`; значение `revision` должно совпадать с префиксом `YYYYMMDD_HHMMSS_<6hex>`. Например: `20260925_092131_a1b2c3_add_user_groups.py` и `revision = "20260925_092131_a1b2c3"`.
- Перед созданием миграции проверь, что её `revision` уникален среди файлов репозитория; `down_revision` указывай на фактическую родительскую миграцию. Не меняй ID уже применённой миграции без плана обновления существующих БД.
- После объединения параллельных веток проверь `alembic heads`: для проекта должна остаться одна вершина. Если появились независимые вершины, согласуй цепочку или создай merge-миграцию Alembic; перед push проверь `alembic upgrade head` на чистой БД.

Ключевые правила:

- модульный монолит;
- FastAPI + React + PostgreSQL;
- backend — источник бизнес-правил;
- REST — каноническое состояние;
- Socket.IO — realtime-уведомления;
- серверное время — источник временных метрик;
- AI и телефония — через адаптеры;
- не добавлять сложную инфраструктуру «на будущее».

Подробности: `docs/architecture.md` и `docs/decisions/ADR-001-foundation.md`.

## Если Codex завис

Не пытайся спасать старую длинную сессию любой ценой.

Если возможно, сначала сохрани состояние. Если нет — открой новую сессию и восстановись из Git:

```text
Продолжи текущую задачу
```

Не проси пользователя пересказывать старый чат, если информация есть в репозитории.
