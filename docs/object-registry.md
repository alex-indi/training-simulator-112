# Реестр объектов города

Реестр даёт генератору сценариев проверяемый контекст места происшествия. Объект не определяет сам по себе тип происшествия или службу 112. Источники открытых данных и будущие импортеры записываются одинаково. Подготовленный импорт московских наборов 747 и 624 описан в [отчёте качества](object-registry-import-report.md), медицинских наборов 502, 517, 503, 505 и 516 — в [медицинском отчёте](object-registry-medical-import-report.md).

## Расширяемая модель

`ObjectType` хранится в таблице `object_types`: уникальный `code`, название, необязательный `parent_id`, описание, источник и признак активности. Типы образуют дерево произвольной глубины. Базовый набор в [`backend/seed/object_types.json`](../backend/seed/object_types.json) — отправная точка, а не допустимый перечень: новый тип, например `SHOPPING_CENTER`, добавляется записью в БД без правки кода или миграции.

```text
BUILDING
├── EDUCATION
│   ├── SCHOOL
│   └── KINDERGARTEN
├── HEALTHCARE
│   ├── HOSPITAL
│   ├── POLYCLINIC
│   └── EMERGENCY_STATION
└── TRANSPORT
    └── METRO_STATION
```

`CityObject` в `city_objects` всегда ссылается на один `ObjectType`. Обязательны `source` и `external_id`; вместе они уникально идентифицируют запись источника. Хранятся название, адрес, район, административная область, координаты, идентификатор набора данных и время создания/обновления. Уникальность пары позволяет двум источникам использовать одинаковый внешний ID. Индексы по типу, району и внешнему ID поддерживают отбор и последующий импорт.

`ObjectAttribute` в `object_attributes` хранит характеристику как `attribute_code`, текстовое `value` и `value_type`. Код уникален внутри объекта. Например, `CAPACITY=800` с типом `integer`, `HAS_CHILDREN=true` с типом `boolean`. Импортер отвечает за корректную сериализацию значения; новые характеристики не требуют столбцов в `city_objects`.

`ObjectTag` в `object_tags` связывает объект с кодом из справочника `object_tags_dictionary`. Справочник содержит `code`, `name` и `description`; начальные определения хранятся в [`backend/seed/object_tags_dictionary.json`](../backend/seed/object_tags_dictionary.json). Один тег у объекта не дублируется. Новый признак добавляется в справочник без изменения схемы. Теги обозначают контекст для сценария и не являются правилом выбора службы или видом происшествия. `critical_objects` доступен в справочнике, но не присваивается всем больницам автоматически: для этого нужны данные о конкретном объекте.

Связь с SRC-006 хранится отдельно в `object_tag_classifier_features`: тег ссылается на существующий `IncidentFeature` по внешнему ключу. Проверенные соответствия загружаются из [`backend/seed/object_tag_classifier_features.json`](../backend/seed/object_tag_classifier_features.json) по составному ключу признака SRC-006. Пока подтверждены `education` → «Учебное заведение» и `transport` → «транспорт». Остальные теги не считаются признаками классификатора автоматически: например, `mass_people` описывает потенциал объекта, а «Скопление людей (10 и более человек)» — уже известное обстоятельство происшествия. Запрос `select_city_objects_for_classifier_features(feature_ids, type_code=...)` использует только явные соответствия. Импорт классификатора и объектов добавляет связи после появления обоих справочников.

## Использование генератором

```text
Open Data Sources → Object Registry → Scenario Generator → Training Incident
```

Запрос `select_city_objects(type_code="BUILDING", tags=["mass_people"])` ищет объекты выбранного типа и всех его потомков с хотя бы одним из заданных тегов. В дерево `BUILDING` входят образовательные, медицинские и транспортные сооружения, поэтому запрос может вернуть школы, станции метро и больницы. Тег `mass_people` означает потенциальное массовое пребывание; при импорте он назначается больницам, но не всем медицинским объектам. Без `type_code` возможен отбор по тегам независимо от дерева. Поэтому сценарий с собственным типом происшествия сможет искать подходящий объект по типу и характеристикам, не привязывая объект напрямую к `ScenarioType` или службам. Генератор и UI пока не реализованы.

## Схема и стартовые данные

Миграция `20260924_14_object_registry` создаёт четыре таблицы, `20260924_15_object_tags_dictionary` добавляет справочник и внешний ключ с сохранением уже записанных тегов, `20260924_16_object_tag_classifier_links` — таблицу связей с SRC-006. После `alembic upgrade head` стартовые типы и определения тегов загружаются вместе с объектами командой `cd backend && uv run python -m scripts.import_city_objects.import_objects load`. Классификатор загружается командой `cd backend && uv run python -m seed.incident_classifier.import_seed`. Порядок двух загрузок может быть любым: подтверждённые связи добавятся, когда оба справочника окажутся в БД. Загрузка повторяема, сохраняет вручную изменённые определения и обновляет существующие объекты по ключу источника.

## Подготовленные исходные наборы Москвы

В [`backend/seed/object_registry/source_data`](../backend/seed/object_registry/source_data) сохранены исходные выгрузки data.mos.ru: набор 747 с 3492 строками образовательных учреждений, набор 624 с 1177 строками входов/выходов метро и пять медицинских наборов с 588 строками. Сырые строки не являются seed `CityObject` и не загружаются в БД автоматически.

У набора 747 есть тип и вид учреждения, но нет координат или структурированного района; юридический адрес и подчинённость приходят текстом. Набор 624 описывает **отдельные входы и выходы**. Mapper агрегирует их по `NameOfStation` и сохраняет ID входов в атрибуте станции. Исходные данные можно обновить [клиентом data.mos.ru](../backend/scripts/import_city_objects/mos_api_client.py), который читает `MOS_API_KEY` из переменной процесса или локального `.env` в корне проекта; для текущего seed сеть не требуется.

Медицинские наборы содержат по несколько физических адресов у части организаций. Mapper создаёт отдельный `CityObject` на каждый адрес с ключом `<global_id строки>:<global_id адреса>` и сохраняет оба исходных ID в атрибутах. Закрытые организации не входят в seed; статус и график работы сохраняются у остальных. Теги `24_hours` и `daytime` добавляются по графику, а не по одному названию типа. В текущих медицинских выгрузках координат нет, поэтому они остаются пустыми; качество и количества приведены в медицинском отчёте.
