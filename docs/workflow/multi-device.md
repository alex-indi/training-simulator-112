# Работа на нескольких устройствах

## Цель

Позволить двум разработчикам бесшовно продолжать работу на рабочем Windows PC, домашнем Windows PC и macOS без переноса папок вручную и без зависимости от сохранности Codex-чата.

## Единственный перенос состояния — Git remote

Запрещённый рабочий процесс:

```text
папка → ZIP → облако/флешка → другой ПК
```

Нормальный процесс:

```text
commit → push → fetch/pull → continue
```

## Первый запуск на новом устройстве

1. установить Git;
2. установить Codex;
3. установить `uv` — нужен в том числе для WEEEK MCP;
4. клонировать репозиторий;
5. создать локальный `.env` на основе `.env.example`;
6. добавить `WEEEK_API_TOKEN`;
7. перезапустить Codex/IDE при необходимости;
8. проверить MCP командой `/mcp` в Codex или через настройки IDE;
9. запустить `$project-resume`.

## Начало рабочего блока

```bash
git fetch --all --prune
git status
git branch --show-current
```

Если продолжается существующая задача:

```bash
git switch feature/UT112-123-example
git pull --ff-only
```

Далее в Codex:

```text
$project-resume
```

## Перед сменой устройства

В Codex:

```text
$project-checkpoint
```

После проверки:

```bash
git push
```

Не уходить с устройства с уникальными полезными изменениями, которые существуют только локально.

## Если задача не завершена

Допускается промежуточный коммит:

```text
chore(UT112-123): сохранить промежуточное состояние
```

или более конкретный логический коммит, если часть работы завершена.

Squash merge не перенесёт служебную историю feature-ветки в `main`.

## Если Codex завис или потерял контекст

Не тратить время на попытки спасать длинную сессию.

1. открыть новую сессию;
2. запустить `$project-resume`;
3. агент восстановит branch, task handoff, diff, recent commits и при наличии WEEEK-задачу;
4. продолжить с `Next step` из task handoff.

## Два разработчика

Каждый работает в своей задаче/ветке и своём `tasks/UT112-xxx.md`.

Это снижает конфликты в общих файлах.

`docs/current-state.md` обычно обновляется после merge или при существенном изменении baseline, а не на каждом локальном шаге.

## Материалы заказчика

`materials/customer/` исключён из Git. Это не мешает обычному продолжению разработки: подтверждённые выводы уже находятся в `docs/`.

Если на новом устройстве нужно заново проверить первоисточник через `$customer-materials`, исходные файлы должны быть отдельно синхронизированы через согласованное приватное хранилище. Не переносить секретные/ограниченные материалы в публичный Git только ради удобства continuity.

## Правило коротких сессий

Не стремиться вести один Codex-чат весь проект.

Нормальный unit работы:

```text
одна задача / логический этап
≈
одна или несколько коротких Codex-сессий
+
один task handoff
```

Если сессия стала нестабильной — создать checkpoint и начать новую.
