# Code Style

## Общий принцип

Код должен быть компактным, но читаемым с первого просмотра. Предпочтение простому решению перед «умным».

Приоритеты:

1. простота;
2. надёжность;
3. лёгкость изменения;
4. скорость разработки;
5. теоретическая архитектурная чистота.

## Python

- `snake_case` — функции и переменные;
- `PascalCase` — классы;
- `UPPER_SNAKE_CASE` — константы;
- type hints почти везде;
- `Any` только на реально динамических границах;
- каждая функция/метод имеет Google-style docstring на русском; для простой функции допустима одна строка;
- комментарии на русском объясняют неочевидное «что/почему»;
- `except Exception` только на верхних/integration boundaries с логированием;
- ожидаемые ошибки обрабатываются централизованно.

## JavaScript / React

- `camelCase` — переменные и функции;
- `PascalCase` — компоненты;
- функциональные компоненты и hooks;
- server state — TanStack Query;
- локальный UI state — `useState`;
- Zustand только при доказанной необходимости;
- MUI + CSS Modules;
- JSDoc для сложных публичных utilities/hooks и структур, не для очевидного кода.

## Имена

Использовать явные полные имена.

Допустимые распространённые сокращения: `id`, `api`, `url`, `http`, `json`, `sql`, `db`, `ui`, `uuid`, `utc`, `html`, `css`.

Избегать `usr`, `sess`, `cfg`, `ctx`, `mgr`, `svc`, `tmp`, `res`, если нет сильной причины.

## Размер и ответственность

Функция ограничивается одной ответственностью, а не жёстким числом строк.

Файл:

- до ~300 строк обычно нормально;
- 300–500 — проверить ответственность;
- более 500 — вероятно пора делить, но ответственность важнее метрики.

## DRY и рефакторинг

- небольшое дублирование лучше преждевременной абстракции;
- рефакторить только в рамках задачи;
- не переписывать соседние модули «заодно».

## Validation

- backend boundary — Pydantic;
- сложные frontend forms — Zod;
- backend остаётся источником бизнес-правил;
- frontend использует `available_actions`.

## Логирование

Логировать:

- ошибки;
- ключевые бизнес-события;
- integration failures.

Не логировать:

- пароли;
- токены;
- cookie;
- Authorization header;
- лишние персональные данные.

## Тесты

- backend business logic всегда тестируется;
- critical UI flows — E2E;
- bug fix обязательно имеет regression test;
- snapshot tests не использовать.

## API

- REST nouns;
- JSON `snake_case`;
- время ISO 8601, backend UTC;
- Socket.IO events: `domain.event`.

## Git

Одна задача = одна ветка.

Commit:

```text
feat(UT112-083): добавить принятие карточки
```

PR:

```text
[UT112-083] Добавить принятие карточки
```

Merge — squash.

## TODO/FIXME

Только с идентификатором задачи:

```text
TODO(UT112-123): ...
```

## Magic values

Бизнес-значения выносить в именованные константы/config там, где это повышает понятность. Не делать механическое извлечение каждой строки/числа.

Бизнес-статусы — enum или централизованные константы.
