# ADR-001 — Базовая архитектура проекта

**Status:** ACCEPTED  
**Date:** 2026-09-21  
**Decision owners:** команда проекта «Учебный тренажер 112»  
**Related:** `docs/architecture.md`, `docs/domain.md`, `docs/state-machines.md`

## Контекст

Проект разрабатывается небольшой командой из двух разработчиков с активным использованием Codex. Работа ведётся на нескольких устройствах и должна оставаться воспроизводимой на Windows и macOS.

Предметная область ещё уточняется вместе с заказчиком, поэтому архитектура должна позволять менять отдельные бизнес-правила без перестройки всей системы.

Подтверждённая продуктовая граница текущего MVP:

```text
Система-112 / Virtual112
        ↓
готовая карточка происшествия
        ↓
диспетчер ДДС
        ↓
решение о реагировании
        ↓
группа реагирования
        ↓
доклады о ходе работ
        ↓
диспетчер обновляет статусы ДДС
```

Для MVP взаимодействие со старшим группы реагирования имитируется встроенным текстовым каналом. Это учебная замена телефонного обмена, а не утверждение о реальном способе работы каждой ДДС.

Основные требования к foundation:

- быстрое начало разработки;
- простота локального запуска;
- работа без обязательного внешнего интернета;
- возможность восстановления состояния после reconnect и обновления страницы;
- хранение полной истории учебных действий;
- возможность позднее добавить телефонию и локальный AI;
- отсутствие преждевременной инфраструктурной сложности;
- возможность двум разработчикам работать параллельно через Git и независимые feature-ветки.

## Решение

### 1. Архитектурный стиль — модульный монолит

Backend реализуется как одно приложение FastAPI, разделённое на предметные модули.

Базовые границы:

```text
identity
organizations
training
incidents
response
assessment
virtual112
realtime
integrations
```

Микросервисы на этапе MVP не используются.

Причина: команда небольшая, предметная модель ещё уточняется, а отдельные сервисы увеличили бы стоимость разработки, тестирования, локального запуска и синхронизации контрактов без текущей пользы.

### 2. Backend

Используется:

- Python 3.12+;
- FastAPI;
- Pydantic / pydantic-settings;
- SQLAlchemy 2;
- Alembic;
- PostgreSQL;
- python-socketio;
- pytest / pytest-asyncio;
- Ruff.

Backend является единственным источником бизнес-правил.

Frontend не должен самостоятельно определять допустимость перехода статуса, обязательность комментария или завершённость карточки.

API возвращает доступные действия, например:

```json
{
  "status": "ACCEPTED",
  "available_actions": [
    "START_RESPONSE"
  ]
}
```

### 3. Frontend

Используется:

- JavaScript;
- React;
- Vite;
- React Router;
- Material UI;
- CSS Modules;
- TanStack Query;
- React Hook Form;
- Zod для сложных форм;
- socket.io-client;
- Playwright для критических E2E-сценариев.

TypeScript не вводится в foundation.

Server state хранится через TanStack Query. Локальное UI-состояние — через React state. Дополнительный глобальный state manager не добавляется без реальной необходимости.

### 4. PostgreSQL — основное хранилище

PostgreSQL является каноническим хранилищем:

- пользователей;
- занятий;
- учебных прохождений;
- карточек;
- назначений групп реагирования;
- сообщений;
- истории действий;
- результатов оценки.

Alembic используется для всех изменений схемы.

### 5. REST — источник состояния, Socket.IO — канал уведомлений

REST является каноническим источником текущего состояния.

Socket.IO используется только для realtime-событий, например:

```text
session.started
incident.delivered
incident.updated
response.message_created
response.state_changed
assessment.completed
```

После reconnect клиент повторно запрашивает актуальное состояние через REST.

Никакое важное состояние не должно существовать только внутри Socket.IO-соединения.

### 6. История действий сохраняется отдельно от текущего состояния

Текущая карточка не является достаточным источником для оценки обучаемого.

Значимые действия фиксируются как отдельные записи `IncidentAction` с серверным временем.

Примеры:

```text
CARD_OPENED
PRIMARY_STATUS_CHANGED
COMMENT_ADDED
RESPONSE_UNIT_ASSIGNED
RESPONSE_TASK_SENT
RESPONSE_MESSAGE_READ
STATUS_CHANGED
CARD_COMPLETED
```

Это позволяет восстанавливать хронологию и оценивать задержки, неправильные и пропущенные действия.

### 7. `TrainingScenario` — отдельное понятие от сценария реагирования Системы-112

Учебные сценарии продукта называются `TrainingScenario`.

Причина: в исходных материалах термин «сценарий реагирования» уже используется как техническое понятие реальной Системы-112 и имеет другой смысл.

### 8. `Virtual112` отделён от работы обучаемого ДДС

`Virtual112` имитирует внешнюю для ДДС часть процесса:

- создаёт готовую учебную карточку;
- доставляет её обучаемому;
- имитирует необходимые внешние изменения;
- позднее может использовать классификатор и routing.

Обучаемый ДДС не обязан заново выполнять первичную классификацию звонка.

### 9. Виртуальная группа реагирования

Для MVP используется:

```text
ResponseUnit
ResponseAssignment
ResponseMessage
```

`ResponseUnit` — идентичность виртуальной группы/бригады.

`ResponseAssignment` — конкретное назначение этой группы на конкретное происшествие.

**Состояние хода реагирования хранится на `ResponseAssignment`, а не на `ResponseUnit`.**

Причина: одна и та же группа может участвовать в разных происшествиях в разные моменты, а состояния `EN_ROUTE`, `ARRIVED`, `WORKING` относятся именно к конкретному назначению.

В будущем `ResponseUnit` при необходимости может получить отдельное состояние доступности (`AVAILABLE`, `BUSY` и т. п.), но это не входит в первый MVP.

### 10. Состояние группы реагирования и статус ДДС независимы

Ключевое правило:

```text
ResponseAssignment = EN_ROUTE
```

не должно автоматически менять статус ДДС на:

```text
Начало реагирования
```

Виртуальная группа создаёт сообщение/событие. Обучаемый читает его, интерпретирует и самостоятельно выполняет действие в карточке.

Это необходимо для обучения и оценки.

### 11. Коммуникация с группой реагирования абстрагирована от транспорта

На первом этапе используется встроенный текстовый чат.

Он моделирует телефонный обмен:

- старший группы может сам сообщить об изменении обстановки;
- диспетчер может самостоятельно запросить состояние.

Позднее текстовый канал может быть дополнен или заменён `TelephonyProvider` без изменения доменной модели `ResponseAssignment`.

### 12. AI не является источником детерминированной истины

Интеграция AI выполняется через provider-интерфейс.

AI может использоваться для:

- анализа свободного текста;
- объяснения ошибок;
- рекомендаций;
- генерации вариаций сценариев.

Правила переходов, временные метрики, обязательные комментарии и другие формализуемые требования проверяются обычным кодом.

Основной учебный flow должен работать без внешнего AI.

### 13. Маршрутизация выделяется как отдельная будущая ответственность

Подтверждено, что выбор ДДС зависит не только от типа происшествия, но также от территории обслуживания и подчинённости объекта.

Будущая модель:

```text
classification
+
service area
+
object affiliation
→
notification targets
```

Полный `RoutingEngine` не реализуется в foundation. Первый vertical slice использует заранее подготовленные данные `TrainingScenario`.

### 14. Локальная разработка и воспроизводимый запуск

В режиме разработки:

```text
PostgreSQL → Docker
Backend → локальный процесс с hot reload
Frontend → Vite dev server
```

После первого vertical slice должен существовать контрольный запуск:

```bash
docker compose up --build
```

который воспроизводимо поднимает проект на поддерживаемых устройствах.

Версии runtime и зависимостей должны фиксироваться в репозитории.

## Последствия

### Положительные

- один репозиторий и одно приложение проще поддерживать двум разработчикам;
- предметные правила можно менять внутри отдельных модулей;
- frontend не дублирует бизнес-логику;
- realtime не становится отдельным источником истины;
- история действий пригодна для оценки и разбора;
- чат можно заменить телефонией без изменения core domain;
- AI можно развивать независимо от базового учебного flow;
- проект можно локально развернуть без сложной инфраструктуры.

### Ограничения и стоимость

- модульные границы придётся дисциплинированно соблюдать внутри одного процесса;
- realtime-события требуют аккуратного восстановления через REST после reconnect;
- JSONB в ранних версиях `TrainingScenario` повышает гибкость, но требует последующей нормализации стабильных данных;
- универсальный MVP workflow не отражает все реальные исключения отдельных ДДС;
- встроенный чат не является полной имитацией реальной телефонной коммуникации.

## Рассмотренные альтернативы

### Микросервисы

Отклонены для MVP: слишком высокая операционная и когнитивная стоимость для команды из двух человек и меняющейся предметной модели.

### Только REST polling без realtime

Не выбран как основной подход: преподавательский мониторинг и сообщения виртуальной группы требуют оперативного обновления UI. При этом REST сохраняется как источник истины.

### Socket.IO как источник состояния

Отклонено: reconnect и смена устройства не должны приводить к потере состояния.

### Полноценная SIP/Asterisk-телефония с первого этапа

Отклонена: заказчик допускает упрощение, а основной учебный workflow можно проверить через текстовый канал.

### Обязательный облачный AI

Отклонён: локальный/offline demo должен оставаться работоспособным.

### Жёсткое моделирование всех ДДС и их исключений сразу

Отклонено: для MVP заказчик допускает универсальный алгоритм, а полная специфика служб существенно увеличивает объём.

## Не решается этим ADR

Следующие вопросы остаются отдельными решениями:

- точная схема аутентификации и хранения пользовательской сессии;
- полный `RoutingEngine`;
- импорт и версия классификатора;
- конкретный набор первых ДДС и сценариев;
- точная методика оценки;
- полный набор редактируемых полей карточки;
- реальная SIP-телефония;
- промышленная схема deployment у заказчика.

## Критерий пересмотра ADR

ADR должен быть пересмотрен, если появляется требование, которое объективно невозможно или существенно дороже реализовать внутри текущего модульного монолита, либо если заказчик требует интеграции с реальным промышленным контуром с иными инфраструктурными ограничениями.
