## Продукт и граница MVP

Основной обучаемый — диспетчер ДДС. Он получает готовую карточку Системы-112, принимает или отклоняет её, самостоятельно меняет статусы карточки и ведёт происшествие к завершению. Виртуальные службы и группы реагирования имеют собственное состояние и чат; их состояние не меняет статус ДДС автоматически.

Целевой демонстрационный путь:

```text
ADMIN настраивает пользователей/справочники/AI
→ INSTRUCTOR выбирает READY-сценарий
→ генерирует пакет вариантов
→ просматривает / исправляет / перегенерирует
→ утверждает пакет в занятие
→ карточки попадают в общий пул или индивидуальную очередь
→ TRAINEE берёт карточку
→ принимает/отклоняет и меняет статусы
→ получает сообщения служб
→ завершает карточку
→ INSTRUCTOR наблюдает занятие и проводит итоговый разбор
```

## Реализовано в `main`

### Платформа

- FastAPI + SQLAlchemy 2 + Alembic + PostgreSQL.
- React + Vite + CSS Modules.
- REST — каноническое состояние; Socket.IO используется для уведомлений и обновления UI.
- Единый локальный запуск через `dev.py`.
- `dev.py` перед запуском сервисов выполняет обычный `alembic upgrade head`, поэтому локальная схема автоматически догоняет актуальные миграции.
- Воспроизводимый bootstrap чистой БД через `app.scripts.bootstrap_demo`.
- Demo-роли: `ADMIN`, `INSTRUCTOR`, `TRAINEE`.

### Занятие и АРМ ДДС

- `TrainingSession`, `TrainingRun`, `TrainingGroup`.
- Режимы `FLOW`, `FIXED_SET`, `MANUAL`.
- Индивидуальные и общие очереди.
- Атомарный claim карточки из общего пула одним обучаемым.
- `Incident` со snapshot исходных данных и неизменяемой историей `IncidentAction`.
- Статусы ДДС, обязательные комментарии, серверные временные метки и `available_actions`.
- Рабочее место обучаемого, реестр карточек и восстановление состояния через REST.

### Виртуальные службы

- `ResponseUnit`, `ResponseAssignment`, `ResponseMessage`.
- Назначение служб и отдельный lifecycle группы реагирования.
- Адресные сценарные сообщения конкретной службе.
- Подготовленные сообщения и переходы группы выпускаются runtime-механизмом.
- Состояние группы реагирования не переводит карточку ДДС автоматически.

### Кабинет преподавателя

- Подготовка занятия и состава АРМ.
- Общие и индивидуальные очереди.
- Live-монитор состояния группы.
- Глобальная и индивидуальная пауза.
- Команды преподавателя, заметки и завершение занятия.
- Итоговый разбор с предварительной автоматической оценкой, подтверждением/снятием сигналов, итоговым баллом и аудитом решений преподавателя.
- Интерфейс приведён к единой визуальной системе АРМ ДДС.

### Классификатор и Object Registry

- Импортирован SRC-006: 1 283 правила классификатора.
- 1 024 признака, 2 816 связей правило–признак.
- 209 служб, 1 179 связей правило–служба.
- Динамическое дерево `ObjectType`.
- Реестр объектов Москвы, атрибуты и семантические теги.
- На чистом bootstrap: 12 типов объектов и 4 638 объектов Москвы.
- В реестр включены образовательные, транспортные и медицинские объекты.

### Библиотека и генератор сценариев

- `ScenarioTemplate` со статусами `DRAFT`, `READY`, `ARCHIVED`.
- Привязка к SRC-006, службам и Object Registry.
- `ScenarioInstance` со snapshot классификатора, объекта, служб, событий и текстов.
- Пакетная генерация нескольких вариантов из одного READY-шаблона.
- Детерминированный выбор объектов и вариантных фактов.
- Просмотр, ручная правка, исключение, перегенерация текста или всей карточки до утверждения.
- Утверждение пакета в общий пул или индивидуальную очередь.
- Подготовленные runtime-события и сообщения служб.
- Основной преподавательский workflow упрощён; старый расширенный редактор не является основным путём проведения занятия.

### AI Text Renderer

- Provider-agnostic `AITextRenderer`.
- OpenAI и OpenAI-compatible provider adapters.
- Настройки AI через административную панель.
- API key хранится на backend и не возвращается клиенту.
- AI используется только для формулировки текстов карточек и сообщений служб.
- Классификация, службы, объекты, события и корректность действий определяются структурированными данными, а не LLM.
- Тексты готовятся до занятия и сохраняются в snapshot; runtime не зависит от доступности внешнего AI.
- При недоступности AI используется детерминированный fallback.

### Панель администратора

- Отдельный `/admin` и backend `/api/admin` с обязательной проверкой роли.
- Пользователи, роли, пароли и пользовательские группы.
- Классификатор, службы, Object Registry и типы объектов.
- Импорт/экспорт справочных данных и история импорта.
- AI provider/model/endpoint/key/health/usage.
- Общая с преподавателем библиотека сценариев.
- Административный аудит и состояние системы.
- `/api/admin/system` читает фактическую текущую Alembic revision из БД.

## Правила библиотеки сценариев

- Черновики `DRAFT` могут совместно исправлять преподаватели и администраторы.
- READY-сценарий нельзя редактировать напрямую: для изменений создаётся копия-черновик.
- **Архивировать READY-сценарий может только его автор или ADMIN.**
- Обучаемый не получает методические данные шаблона, ожидаемые действия и скрытые критерии.

## Что осталось до demo-ready MVP

### P0 — обязательно

1. Провести полный пользовательский acceptance-smoke на чистой БД от ADMIN до итогового разбора.
2. Проверить реальный AI provider и отдельно проверить полноценный fallback без AI/интернета.
3. Проверить общий пул двумя обучаемыми, конкурентный claim и сообщения разных служб.
4. Проверить refresh/reconnect браузера во время активного занятия.
5. Подготовить набор демонстрационных READY-сценариев, а не один технический seed.
6. Провести финальную интеграционную стабилизацию и многократный demo-run.

### P1 — после прохождения основного пути

- расширить библиотеку сценариев по направлениям пожар / ДТП / ЖКХ / медицина / транспорт;
- дополнительно отполировать Live Monitor и АРМ ДДС;
- расширить автоматическую оценку только там, где это подтверждено методикой;
- провести LAN-нагрузочный smoke на целевом количестве рабочих мест.

### Не является обязательным для текущего MVP

- SIP/Asterisk и настоящая телефония;
- микросервисы, Redis, Kafka, Celery, Kubernetes;
- генерация LLM бизнес-фактов сценария во время занятия;
- сложный универсальный rule engine;
- полная production-аутентификация.

## Технические решения, которые не пересматриваем до демонстрации

- модульный монолит;
- PostgreSQL как источник долговременного состояния;
- REST как источник истины для клиента;
- Socket.IO только как механизм уведомлений;
- бизнес-правила находятся на backend;
- AI не принимает доменных решений;
- изменения шаблонов не меняют уже созданные `ScenarioInstance` и `Incident`;
- общий пул сохраняется и использует атомарный claim.
