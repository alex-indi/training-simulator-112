# Текущее состояние проекта

**Дата:** 21.09.2026  
**Проект:** «Учебный тренажер 112»  
**Идентификатор:** `UT112`

## Что уже определено

### Предметная модель

- основной обучаемый — диспетчер ДДС;
- он получает готовую карточку Системы-112;
- после `Принята` реагирование организуется внутри службы;
- решение принимает диспетчер при наличии полномочий либо руководство;
- старший группы реагирования докладывает в ДДС о ходе работ либо диспетчер сам связывается с ним;
- реальные каналы: телефон, радио, внутренние средства; для тренажера достаточно телефона;
- внутренние процессы служб различаются и не моделируются универсально.

### Решение MVP по реагированию

- создаётся виртуальная группа реагирования;
- обучаемый вручную назначает её на карточку;
- группа симулирует реагирование;
- обмен информацией в первом MVP идёт через встроенный онлайн-чат;
- чат имитирует телефонный обмен;
- состояние группы и статус ДДС разделены;
- обучаемый самостоятельно меняет статус карточки после получения сообщения.

### Маршрутизация

Заказчик уточнил, что состав ДДС зависит от района обслуживания и подчинённости объекта, а не только от типа происшествия.

Полный RoutingEngine откладывается; первый vertical slice использует подготовленные данные сценария.

## Project Continuity Layer

Подготовлены правила для бесшовной работы двух разработчиков на нескольких устройствах:

- Git — долговременная память проекта;
- `tasks/UT112-xxx.md` — handoff конкретной задачи;
- `docs/current-state.md` — только состояние `main`;
- `docs/decision-log.md` — хронология решений;
- `$project-resume` — восстановление новой сессии;
- `$project-checkpoint` — сохранение состояния перед паузой/сменой устройства;
- `.codex/config.toml` — общий project-level Codex config;
- WEEEK MCP подключается без хранения токена в Git.
