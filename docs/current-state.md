# Текущее состояние MVP

**Актуально на 26.09.2026.** Этот документ описывает работающую модель тренажёра после упрощения сценариев и подготовки занятия.

## Основной путь

ADMIN настраивает пользователей, справочники и AI → INSTRUCTOR создаёт занятие, выбирает группы и заранее готовит карточки → TRAINEE занимает АРМ и работает с карточками ДДС → INSTRUCTOR наблюдает занятие и проводит итоговый разбор.

Карточка происшествия уже содержит все факты, необходимые обучаемому. ДДС сам принимает или отклоняет карточку, затем вручную меняет статусы своей службы. Сообщения виртуальных служб и учебной бригады не меняют статус ДДС автоматически.

## Подготовка занятия преподавателем

Подготовка состоит из четырёх шагов:

1. **Параметры занятия** — название, режим выдачи, длительность/интервал и порядок карточек.
2. **Группы** — постоянные группы добавляются в занятие до подключения класса. Для группы выбирается общий или личный пул.
3. **Карточки происшествий** — преподаватель формирует набор из шаблона либо добавляет ранее сохранённые карточки. Он проверяет объект, адрес, условия и текст карточки, может перегенерировать текст или карточку, исключить неудачную и сохранить удачную в библиотеку.
4. **Подключение и запуск** — обучаемые занимают АРМ, получают группу занятия и после проверки готовности запускается тренировка.

Старый конструктор временной шкалы, дополнительных событий и ручного программирования сообщений служб не является частью обычного MVP-интерфейса преподавателя. Его backend-модели пока сохранены для совместимости, но не нужны для подготовки занятия.

## Шаблоны и карточки

`ScenarioTemplate` хранит методическую основу: тип происшествия, правило выбора объекта, сложность, допустимые варианты фактов и участвующие службы. В интерфейсе преподавателя технические коды не показываются.

Из одного шаблона до занятия генерируется несколько разных `ScenarioInstance`. Факты и объект выбираются детерминированно по seed, после чего AI (или шаблонный fallback) формулирует короткий текст карточки. Готовый экземпляр можно сохранить как `SavedIncidentCard` и использовать повторно в других занятиях.

После подтверждения карточки попадают в очередь занятия. Для `SHARED_QUEUE` одна карточка видна всей группе, а первый claim атомарно закрепляет её за одним `TrainingRun`. Для `INDIVIDUAL_QUEUE` карточки адресуются конкретному АРМ.

## Runtime ДДС 101

После принятия карточки:

- остальные службы, указанные в snapshot сценария, дают воспроизводимую первичную реакцию;
- учебная бригада 101 проходит этапы `Выехали → Прибыли → Работают → Завершили`;
- этапы выпускаются по учебному времени с учётом пауз;
- ДДС должен сам поставить соответствующие статусы карточки;
- состояние бригады и статусы ДДС независимы.

Для MVP интервалы сообщений бригады разнесены так, чтобы на каждый этап сохранялся полный норматив реакции ДДС 45 секунд.

## Оценивание

После завершения занятия система строит предварительный воспроизводимый результат по фактической истории:

- первичное решение по карточке;
- реакция на сообщения бригады;
- пропуски обязательных статусов;
- последовательность действий;
- незавершённые карточки;
- обязательные комментарии при отказе.

Паузы исключаются из учебного времени. AI может сформулировать текстовое резюме только по рассчитанным фактам и отклонениям. Итоговую оценку и решение подтверждает преподаватель; его изменения аудируются.

## Техническая база

- Backend: FastAPI, SQLAlchemy 2, Alembic, PostgreSQL.
- Frontend: React + Vite, JavaScript, CSS Modules.
- REST — каноническое состояние; Socket.IO — уведомления.
- `dev.py` применяет миграции и запускает локальный стенд одной командой.
- `bootstrap_demo` и `seed_all` восстанавливают воспроизводимые CORE/DEMO данные.
- SRC-006, каталог служб, Object Registry и московские объекты импортируются из версионированных seed-файлов.
- `AITextRenderer` поддерживает OpenAI/OpenAI-compatible provider и детерминированный fallback. AI не выбирает классификацию, службы, объект или бизнес-переходы.
- Планировщик использует PostgreSQL advisory lock: при нескольких backend-процессах активным scheduler становится только один процесс, остальные периодически пытаются принять лидерство.

## Проверки перед merge/release

Обязательные автоматические проверки:

```bash
cd backend
uv run ruff check .
uv run pytest -q

cd ../frontend
npm run lint
npm run build
npm run test:e2e:mvp
```

MVP Playwright smoke работает на отдельной PostgreSQL и проверяет подготовку занятия, общий пул, claim карточки и основной путь ДДС. CI не должен использовать рабочую БД.

## Осознанные ограничения MVP

- demo-аутентификация через локального пользователя/X-Demo-User не является промышленной auth-схемой;
- нет прямой интеграции с промышленной Системой-112;
- нет SIP/Asterisk;
- нет генерации бизнес-фактов LLM во время занятия;
- старые расширенные модели Scenario Engine остаются в backend как технический долг, но не должны возвращаться в обычный интерфейс преподавателя;
- микросервисная инфраструктура, Redis/Celery/Kafka для текущего стенда не требуются.
