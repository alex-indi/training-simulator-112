# Текущее состояние MVP

**Актуально на 26.09.2026.** Этот документ описывает работающую модель тренажёра после упрощения сценариев и подготовки занятия.

## Основной путь

ADMIN настраивает пользователей, справочники и AI → INSTRUCTOR создаёт занятие, выбирает группы и заранее готовит карточки → TRAINEE занимает АРМ и работает с карточками ДДС → INSTRUCTOR наблюдает занятие и проводит итоговый разбор.

```text
Шаблон инцидента → генерация нескольких карточек → предварительный просмотр →
сохранение/добавление в занятие → общий или личный пул → обучаемый берёт карточку →
принимает/отклоняет → получает сообщения виртуальных служб → вручную меняет
статусы ДДС → завершает карточку → assessment → преподаватель подтверждает итог
```

Карточка происшествия уже содержит все факты, необходимые обучаемому. ДДС сам принимает или отклоняет карточку, затем вручную меняет статусы своей службы. Сообщения виртуальных служб и учебной бригады не меняют статус ДДС автоматически.

## Подготовка занятия преподавателем

Подготовка состоит из четырёх шагов:

1. **Параметры занятия** — название, режим выдачи, длительность/интервал и порядок карточек.
2. **Группы** — преподаватель выбирает постоянные группы и при необходимости выделяет временные подгруппы из их участников. Подгруппа может объединять обучаемых из разных постоянных групп. Для каждой рабочей группы задаются сложность и общий или личный пул; постоянное членство пользователей не меняется.
3. **Карточки происшествий** — преподаватель формирует набор из шаблона, добавляет ранее сохранённые карточки по отдельности либо выбирает пакет карточек из библиотеки. Он видит основную классификацию, проверяет объект, адрес, условия и текст карточки, может добавить короткие текстовые условия для формирования итогового текста, перегенерировать текст или карточку, исключить неудачную и сохранить удачную в библиотеку. Сохранённая карточка в библиотеке открывается в таком же редакторе условий и текста; действия добавления в занятие доступны при выборе карточек для группы.
4. **Подключение и запуск** — участники выбранных групп автоматически добавляются в занятие, когда занимают АРМ; это работает и если они заняли АРМ до выбора группы. После проверки готовности преподаватель запускает тренировку.

Старый конструктор временной шкалы, дополнительных событий, ожидаемых действий ДДС и ручного программирования сообщений служб не является частью обычного MVP-интерфейса преподавателя. Его backend-модели сохранены как legacy/internal. Шаблон не содержит универсальный порядок действий ДДС: оценивание строится из фактической истории карточки и правил assessment.

## Шаблоны и карточки

Обычный новый `ScenarioTemplate` хранит методическую основу: тип происшествия, правило выбора объекта, сложность и допустимые варианты фактов. Службы определяются классификатором; ранее сохранённые legacy-шаблоны могут содержать дополнительные ручные связи. В интерфейсе преподавателя технические коды не показываются.

Из одного шаблона до занятия генерируется несколько разных `ScenarioInstance`. Факты и объект выбираются детерминированно по seed, после чего AI (или шаблонный fallback) формулирует короткий текст карточки. Готовый экземпляр можно сохранить как `SavedIncidentCard` и использовать повторно в других занятиях. Сохранённые карточки можно объединять в именованные пакеты, в том числе отбирая их по шаблону. Добавление пакета создаёт копии всех его карточек для выбранной группы и пропускает карточки, уже находящиеся в ней.

После добавления карточки попадают в очередь занятия. `SHARED_QUEUE` — основной режим MVP: одна карточка видна всей группе, а первый claim атомарно закрепляет её за одним `TrainingRun`. `INDIVIDUAL_QUEUE` поддерживается для адресации конкретному АРМ.

Если задана продолжительность занятия, сервер автоматически завершает его после истечения этого учебного времени. Глобальная пауза останавливает отсчёт; незавершённые карточки остаются в истории для разбора.

## Runtime ДДС 101

После принятия карточки:

- только службы из `scenario_services`/`notified_services` snapshot дают первичную реакцию; по умолчанию 102 и 103 принимают карточку, независимо от `Incident.id`; явная `initial_reaction` в snapshot может задать принятие или отказ;
- учебная бригада 101 проходит этапы `Выехали → Прибыли → Работают → Завершили`;
- этапы выпускаются по учебному времени с учётом пауз;
- ДДС должен сам поставить соответствующие статусы карточки;
- состояние бригады и статусы ДДС независимы.

Для MVP этапы бригады после принятия идут на +15, +75, +135 и +195 секундах учебного времени. Каждый этап даёт ДДС полные 45 секунд на реакцию; паузы занятия и индивидуального АРМ исключаются. Состояние бригады не меняет статус ДДС автоматически.

## Оценивание

После завершения занятия система строит предварительный воспроизводимый результат по фактической истории:

- первичное решение по карточке;
- реакция на сообщения бригады;
- пропуски обязательных статусов;
- последовательность действий;
- незавершённые карточки;
- обязательные комментарии при отказе.

Паузы исключаются из учебного времени. Текстовое резюме формируется по кнопке преподавателя только из рассчитанных фактов и отклонений; при недоступности AI используется фактический шаблонный текст. Итоговую оценку и решение подтверждает преподаватель; его изменения аудируются.

## Техническая база

- Backend: FastAPI, SQLAlchemy 2, Alembic, PostgreSQL.
- Frontend: React + Vite, JavaScript, CSS Modules.
- REST — каноническое состояние; Socket.IO — уведомления.
- `dev.py` применяет миграции и запускает локальный стенд одной командой.
- `bootstrap_demo` и `seed_all` восстанавливают воспроизводимые CORE/DEMO данные.
- SRC-006, каталог служб, Object Registry и московские объекты импортируются из версионированных seed-файлов.
- `AITextRenderer` поддерживает OpenAI/OpenAI-compatible provider и детерминированный fallback. AI формулирует текст карточки и summary по рассчитанным фактам, но не выбирает классификацию, службы, объект, реакцию служб, статусы, оценку или бизнес-переходы.
- Backend MVP запускается одним worker/process. Планировщик дополнительно использует PostgreSQL advisory lock для защиты от случайного параллельного запуска.

## Проверки перед merge/release

Обязательные автоматические проверки:

```bash
cd backend
uv run ruff check .
uv run pytest -q

cd ../frontend
npm run lint
npm run build
npm run test:e2e:mvp
```

MVP Playwright smoke работает на отдельной PostgreSQL и проверяет подготовку занятия, общий пул, claim карточки и основной путь ДДС. CI не должен использовать рабочую БД.

## Осознанные ограничения MVP

- demo-аутентификация через локального пользователя/X-Demo-User не является промышленной auth-схемой;
- нет прямой интеграции с промышленной Системой-112;
- нет SIP/Asterisk;
- нет генерации бизнес-фактов LLM во время занятия;
- старые расширенные модели Scenario Engine остаются в backend как технический долг, но не должны возвращаться в обычный интерфейс преподавателя;
- микросервисная инфраструктура, Redis/Celery/Kafka для текущего стенда не требуются.
