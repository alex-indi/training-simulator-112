# Initial backlog — Учебный тренажер 112

Этот файл хранит стартовый набор задач проекта для синхронизации с WEEEK.

Правила:
- идентификаторы задач: `UT112-N`;
- перед созданием задачи в WEEEK нужно проверить, нет ли уже задачи с таким ID;
- новые задачи создавать без исполнителя;
- рабочая доска WEEEK: `К работе → В работе → Готово`;
- этот файл описывает первоначальный backlog, а текущее состояние выполнения хранится в WEEEK;
- не создавать дубликаты задач при повторной синхронизации.

---

## UT112-3 — Bootstrap приложения

**Тип:** infrastructure / foundation  
**Зависит от:** UT112-1  
**Начальный статус WEEEK:** К работе

### Цель

Создать минимальный рабочий каркас проекта «Учебный тренажер 112».

Backend — FastAPI.  
Frontend — React + Vite.

На этом этапе предметную бизнес-логику не реализовывать.

### Критерии готовности

- существует каталог `backend/`;
- существует каталог `frontend/`;
- FastAPI-приложение запускается локально;
- реализован endpoint `GET /health`;
- React-приложение запускается локально;
- frontend отображает стартовый экран тренажера;
- определены понятные команды запуска backend и frontend;
- README содержит команды локального запуска;
- `.env.example` актуален;
- секреты и локальный `.env` не попадают в Git.

## UT112-4 — PostgreSQL и миграции

**Тип:** backend / infrastructure  
**Зависит от:** UT112-3  
**Начальный статус WEEEK:** К работе

### Цель

Подключить PostgreSQL как основное хранилище данных и настроить SQLAlchemy 2 + Alembic.

### Критерии готовности

- backend подключается к PostgreSQL;
- параметры подключения берутся из environment;
- SQLAlchemy 2 настроен;
- Alembic настроен;
- существует первая миграция;
- миграции применяются одной понятной командой;
- приложение корректно запускается после применения миграций;
- конфигурация не содержит секретов в Git.

## UT112-5 — Пользователи и роли

**Тип:** backend / domain  
**Зависит от:** UT112-4  
**Начальный статус WEEEK:** К работе

### Цель

Реализовать базовую модель пользователей тренажера для ролей:

- `ADMIN`;
- `INSTRUCTOR`;
- `TRAINEE`.

Для MVP нужна только функциональность, необходимая локальному демонстрационному стенду.

### Критерии готовности

- существует модель `User`;
- роли представлены enum или эквивалентной централизованной моделью;
- создаются демонстрационные пользователи всех трех ролей;
- backend может определить роль текущего пользователя;
- frontend может учитывать роль при отображении интерфейса;
- не реализуются OAuth, восстановление пароля и другие функции, не нужные MVP.

## UT112-6 — Базовая учебная сессия

**Тип:** backend / domain  
**Зависит от:** UT112-4, UT112-5  
**Начальный статус WEEEK:** К работе

### Цель

Реализовать базовую учебную сессию, в рамках которой преподаватель запускает занятие, а обучаемый выполняет задания.

### Критерии готовности

- существует сущность `TrainingSession`;
- преподаватель может создать учебную сессию;
- у сессии есть состояние;
- преподаватель может запустить сессию;
- обучаемый может быть связан с сессией;
- время старта фиксируется сервером;
- после перезагрузки приложения состояние сессии восстанавливается из БД.

## UT112-7 — Базовая карточка происшествия 112

**Тип:** backend / domain  
**Зависит от:** UT112-4, UT112-6  
**Начальный статус WEEEK:** К работе

### Цель

Реализовать серверную модель готовой карточки происшествия, которую виртуальная Система-112 передает в ДДС.

Обучаемый не формирует первичное обращение самостоятельно — он получает готовую карточку.

### Критерии готовности

- существует сущность `Incident`;
- карточка связана с учебной сессией;
- сохраняются основные сведения о происшествии;
- сохраняются `delivered_at`, `opened_at`, `primary_status_at`;
- существует REST API получения карточки;
- карточка хранит snapshot исходных данных учебного сценария;
- изменение сценария после создания карточки не изменяет уже созданный `Incident`;
- сервер является источником временных метрик.

## UT112-8 — Рабочее место обучаемого: реестр и карточка

**Тип:** frontend / product  
**Зависит от:** UT112-3, UT112-7  
**Начальный статус WEEEK:** К работе

### Цель

Создать основной интерфейс обучаемого: реестр поступивших карточек и просмотр выбранной карточки.

Интерфейс должен постепенно приближаться к логике реального АРМ ДДС и учитывать материалы заказчика.

### Критерии готовности

- отображается реестр поступивших карточек;
- новая карточка визуально заметна;
- карточку можно открыть;
- отображаются основные данные происшествия;
- факт и время открытия фиксируются backend;
- после обновления страницы данные не пропадают;
- интерфейс подготовлен для дальнейшего добавления действий и статусов;
- карточка и реестр имеют единую визуальную структуру.

## UT112-9 — Основной workflow статусов ДДС

**Тип:** backend + frontend / domain  
**Зависит от:** UT112-7, UT112-8  
**Начальный статус WEEEK:** К работе

### Цель

Реализовать основные решения диспетчера ДДС и изменение статуса карточки.

Первый набор действий:

- `Принята`;
- `Не принята`;
- `Начало реагирования`;
- `Прибытие`;
- `Проведение работ`;
- `Работы завершены`;
- `Отказ от выполнения работ`.

### Критерии готовности

- backend определяет допустимые следующие действия;
- frontend получает список `available_actions`;
- недопустимый переход нельзя выполнить прямым запросом к API;
- `Не принята` требует комментарий;
- `Отказ от выполнения работ` требует комментарий;
- значимые действия записываются в `IncidentAction`;
- сохраняется точное серверное время каждого действия;
- `Не принята` может в дальнейшем перейти в `Принята`, если это допускает state machine;
- workflow соответствует `docs/state-machines.md`.

## UT112-10 — Виртуальная группа реагирования

**Тип:** backend / domain  
**Зависит от:** UT112-7, UT112-9  
**Начальный статус WEEEK:** К работе

### Цель

Реализовать виртуальную группу/бригаду, которую диспетчер ДДС может назначить на происшествие.

### Критерии готовности

- существует сущность `ResponseUnit`;
- существует сущность `ResponseAssignment`;
- группа может быть назначена на конкретный `Incident`;
- состояние назначения хранится в `ResponseAssignment`, а не в `ResponseUnit`;
- поддерживаются состояния:
  - `ASSIGNED`;
  - `ACKNOWLEDGED`;
  - `EN_ROUTE`;
  - `ARRIVED`;
  - `WORKING`;
  - `COMPLETED`;
- состояние группы не изменяет статус карточки ДДС автоматически;
- одна и та же `ResponseUnit` может использоваться в разных назначениях.

## UT112-11 — Связь с виртуальной группой реагирования

**Тип:** backend + frontend / product  
**Зависит от:** UT112-10  
**Начальный статус WEEEK:** К работе

### Цель

Реализовать текстовый обмен сообщениями между диспетчером ДДС и виртуальной группой реагирования.

Для MVP чат имитирует оперативный телефонный канал связи.

### Критерии готовности

- обучаемый может отправить сообщение группе;
- виртуальная группа может отправить сообщение обучаемому;
- сообщения сохраняются в БД;
- сообщение связано с конкретным `ResponseAssignment`;
- учебный сценарий может инициировать автоматические сообщения группы;
- обучаемый может запросить текущее состояние группы;
- сообщение группы само по себе не меняет статус карточки;
- после перезагрузки страницы история сообщений сохраняется.

### Пример учебной логики

Группа сообщает:

> Прибыли на место. Наблюдается открытое горение.

Обучаемый должен самостоятельно выполнить действие:

> `Прибытие`

## UT112-12 — Монитор преподавателя

**Тип:** frontend + realtime / product  
**Зависит от:** UT112-6, UT112-9, UT112-11  
**Начальный статус WEEEK:** К работе

### Цель

Создать экран преподавателя для наблюдения за ходом учебной сессии в реальном времени.

### Критерии готовности

- преподаватель видит активную учебную сессию;
- видит карточки, поступившие обучаемому;
- видит текущий статус каждой карточки;
- видит значимые действия обучаемого;
- видит серверное время действий;
- видит сообщения виртуальной группы;
- изменения появляются без ручного обновления страницы;
- realtime используется как уведомление, а REST остается источником канонического состояния.

## UT112-13 — Первый демонстрационный сценарий

**Тип:** product / integration  
**Зависит от:** UT112-6, UT112-7, UT112-9, UT112-10, UT112-11, UT112-12  
**Начальный статус WEEEK:** К работе

### Цель

Реализовать первый полностью проходимый учебный сценарий для демонстрации заказчику.

### Сценарий

1. Преподаватель запускает учебную сессию.
2. `Virtual112` передает обучаемому готовую карточку.
3. Обучаемый открывает карточку.
4. Обучаемый выбирает `Принята`.
5. Обучаемый назначает виртуальную группу реагирования.
6. Группа сообщает: «Задание получили».
7. Группа сообщает: «Выехали».
8. Обучаемый устанавливает `Начало реагирования`.
9. Группа сообщает: «Прибыли».
10. Обучаемый устанавливает `Прибытие`.
11. Группа сообщает: «Приступили к работам».
12. Обучаемый устанавливает `Проведение работ`.
13. Группа сообщает: «Работы завершены».
14. Обучаемый вводит итоговый комментарий.
15. Обучаемый устанавливает `Работы завершены`.
16. Преподаватель видит всю последовательность действий и времени.

### Критерии готовности

- сценарий проходит от начала до конца без ручной правки БД;
- все действия обучаемого сохраняются;
- сообщения виртуальной группы сохраняются;
- состояние восстанавливается после перезагрузки страницы;
- преподаватель видит ход сценария;
- для демонстрации не требуется вручную менять код или данные;
- результат можно воспроизвести повторным запуском сценария.
