# Продукт

## Назначение

«Учебный тренажер 112» — локальное приложение для подготовки диспетчеров дежурно-диспетчерских служб к работе с карточками происшествий, поступающими из Системы-112.

Основной обучаемый MVP — **диспетчер ДДС**.

## Разделение ролей

### Оператор Службы-112

Работает до передачи карточки в ДДС:

```text
первичное сообщение
→ карточка
→ признаки / опросная карта
→ итоговый тип происшествия
→ формирование списка оповещения
→ отправка карточки
```

### Диспетчер ДДС

Работает после поступления готовой карточки:

```text
готовая карточка
→ проверка и анализ
→ Принята / Не принята
→ организация реагирования своей службы
→ связь с группой реагирования
→ статусы и комментарии
→ завершение
```

## Что должен тренировать продукт

Обучаемый должен уметь:

- быстро заметить и открыть карточку;
- проверить содержащиеся сведения и заметить значимые ошибки;
- определить, относится ли происшествие к его службе;
- корректно принять или отклонить карточку;
- назначить реагирующую группу в учебном контуре;
- получать и интерпретировать оперативные сообщения;
- своевременно менять статусы своей службы;
- писать необходимые комментарии;
- действовать при изменении обстановки;
- работать с несколькими карточками;
- получать объяснимый разбор действий.

## Реальный процесс реагирования — подтверждённая часть

По ответу заказчика от 21.09.2026:

- используются доступные средства связи: телефон, радиостанция и внутренние каналы;
- в тренажере разрешено ограничиться телефоном;
- решение о реагировании принимает диспетчер при наличии полномочий, иначе руководство;
- информацию о ходе работ сообщает старший группы реагирования;
- возможны оба режима: старший сам звонит в ДДС или диспетчер сам связывается с ним через некоторое время;
- внутренний процесс у разных служб различается.

Поэтому продукт не пытается воспроизводить внутреннюю диспетчерскую систему каждой ДДС.

## Виртуальная группа реагирования — решение MVP

Для первого MVP взаимодействие с реагирующей группой моделируется встроенным онлайн-чатом.

```text
Incident
  ↓
диспетчер принимает карточку
  ↓
назначает Virtual Response Unit
  ↓
отправляет задачу
  ↓
группа имитирует ход реагирования
  ↓
чат: «выехали / прибыли / приступили / завершили»
  ↓
обучаемый сам обновляет статус ДДС
```

Чат является **учебным заменителем телефонного обмена**, а не утверждением, что реальная ДДС работает в чате.

### Два независимых состояния

Состояние виртуальной группы и статус службы в карточке не синхронизируются автоматически.

Например:

```text
ResponseAssignment = EN_ROUTE
```

не должно автоматически переводить карточку в `Начало реагирования`.
Обучаемый обязан получить сообщение, понять его смысл и выполнить правильное действие.

Это позволяет оценивать:

- правильность статуса;
- скорость реакции;
- пропущенные сообщения;
- преждевременные действия;
- инициативное уточнение обстановки.

## Маршрутизация карточки по службам

Последний ответ заказчика уточнил, что список ДДС определяется не только видом происшествия.

Учитываются как минимум:

```text
характер / признаки происшествия
+
район обслуживания
+
подчинённость объекта
→
список оповещаемых ДДС
```

Пример заказчика: при пожаре в школе района Щукино с пострадавшими информация может одновременно поступить центральным службам 01/02/03, ДДС Департамента образования, ДДС управы района и ДДС административного округа.

## Пользователи

### ADMIN

Пользователи, роли, ДДС, справочники, технические параметры.

### INSTRUCTOR

- создаёт и утверждает учебные сценарии;
- формирует занятие;
- назначает обучаемых;
- запускает и завершает смену;
- наблюдает за действиями в реальном времени;
- видит карточки, сообщения и временную шкалу;
- анализирует ошибки;
- подтверждает или корректирует автоматическую оценку.

### TRAINEE

- получает карточки;
- анализирует их;
- принимает решение;
- назначает виртуальную группу реагирования;
- взаимодействует с ней;
- меняет статусы и вводит комментарии;
- завершает обработку;
- получает разбор.

## TrainingScenario

Для учебных сценариев используем термин `TrainingScenario`, чтобы не путать его с техническим «сценарием реагирования» Системы-112.

```text
TrainingScenario
├── initial_incident
├── expected_result
└── timeline
    ├── карточка поступила
    ├── группа приняла задачу
    ├── группа выехала
    ├── группа прибыла
    ├── изменение обстановки
    └── работы завершены
```

На первом этапе timeline детерминированный. AI может добавляться позднее.

## Оценивание

Детерминированно проверяются:

- время;
- обязательные действия;
- правильность статусов;
- обязательность комментариев;
- последовательность;
- реакция на сообщения группы;
- завершение сценария.

AI используется только там, где нужна семантика свободного текста, объяснение ошибок или вариативность сценариев.

Решение преподавателя выше автоматической оценки.

## Интерфейс

Заказчик просит стремиться повторить цвета и конфигурацию реального АРМ. Карточка и реестр обращений должны быть наиболее похожими; новые и второстепенные экраны могут отличаться.

## Первый vertical slice

```text
преподаватель запускает занятие
→ обучаемому поступает карточка
→ обучаемый открывает её
→ принимает
→ назначает виртуальную группу
→ отправляет задачу
→ получает сообщение группы в чате
→ вручную меняет статус карточки
→ backend сохраняет действие и время
→ преподаватель видит историю
```

Этот поток должен переживать обновление страницы и повторное подключение.

## Не входит в первый каркас

- реальное подключение к Системе-112;
- реальная радиосвязь;
- полноценная SIP/Asterisk-инфраструктура;
- моделирование внутренних систем каждой ДДС;
- все ведомственные исключения сразу;
- обязательный облачный AI;
- микросервисы.
