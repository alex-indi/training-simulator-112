# Продукт

## Назначение

«Учебный тренажер 112» — локальное приложение для подготовки диспетчеров дежурно-диспетчерских служб к работе с карточками происшествий, поступающими из Системы-112.

Основной обучаемый MVP — **диспетчер ДДС**.

## Разделение ролей

### Оператор Службы-112

Работает до передачи карточки в ДДС:

```text
первичное сообщение
→ карточка
→ признаки / опросная карта
→ итоговый тип происшествия
→ формирование списка оповещения
→ отправка карточки
```

### Диспетчер ДДС

Работает после поступления готовой карточки:

```text
готовая карточка
→ проверка и анализ
→ Принята / Не принята
→ организация реагирования своей службы
→ связь с группой реагирования
→ статусы и комментарии
→ завершение
```

## Что должен тренировать продукт

Обучаемый должен уметь:

- быстро заметить и открыть карточку;
- проверить содержащиеся сведения и заметить значимые ошибки;
- определить, относится ли происшествие к его службе;
- корректно принять или отклонить карточку;
- назначить реагирующую группу в учебном контуре;
- получать и интерпретировать оперативные сообщения;
- своевременно менять статусы своей службы;
- писать необходимые комментарии;
- действовать при изменении обстановки;
- учитывать, что карточка из ВИС может быть неполной, а список оповещения может измениться после её доработки;
- распознавать дубли карточек и сообщать, по какой карточке ведётся реагирование;
- корректно взаимодействовать с отделом контроля реагирования;
- работать с несколькими карточками;
- получать объяснимый разбор действий.

## Реальный процесс реагирования — подтверждённая часть

По ответу заказчика от 21.09.2026:

- используются доступные средства связи: телефон, радиостанция и внутренние каналы;
- в тренажере разрешено ограничиться телефоном;
- решение о реагировании принимает диспетчер при наличии полномочий, иначе руководство;
- информацию о ходе работ сообщает старший группы реагирования;
- возможны оба режима: старший сам звонит в ДДС или диспетчер сам связывается с ним через некоторое время;
- внутренний процесс у разных служб различается.

Поэтому продукт не пытается воспроизводить внутреннюю диспетчерскую систему каждой ДДС.

По SRC-002 подтверждено:

- `Добавлена` и `Получена службой` — системные события истории службы, а не действия диспетчера;
- норматив 30 секунд для `Принята` / `Не принята` считается от направления карточки в службу;
- `Не принята` может быть исправлена на `Принята`;
- после `Принята` реальный АРМ предоставляет все дальнейшие статусы, поэтому их строгая backend-цепочка не соответствует источнику;
- ошибочная `Принята`, когда реагирования не будет, исправляется через `Отказ от выполнения работ` с комментарием;
- `Работы завершены` и `Отказ от выполнения работ` закрывают обычное редактирование карточки;
- комментарий обязателен для `Не принята` и `Отказ от выполнения работ`, а содержательные комментарии к промежуточным статусам нужны для информирования о ходе работ;
- дополнительная информация о происшествии отражается в комментариях;
- при изменении ситуации и необходимости других служб диспетчер звонит в `112`, а не редактирует список оповещения самостоятельно;
- общий статус карточки Системы-112 (`Зарегистрирована`, `Отработана`, `Проверена`, `Не оповещено`, `Отказ`, `Не завершено`, `Завершена`) существует отдельно от статуса конкретной службы;
- карточки из ВИС могут содержать неполный набор полей, а после их доработки список оповещения может расшириться.

Решение продукта для MVP:

- backend предоставляет после `Принята` все последующие действия, которые ещё можно записать;
- `Assessment` оценивает пропуск, преждевременность и порядок этапов по фактам `TrainingScenario`, а не превращает учебную ошибку в транспортный запрет API;
- общий статус Системы-112 хранится/показывается отдельно от технического lifecycle учебной карточки.

## Виртуальная группа реагирования — решение MVP

Для первого MVP взаимодействие с реагирующей группой моделируется встроенным онлайн-чатом.

```text
Incident
  ↓
диспетчер принимает карточку
  ↓
назначает Virtual Response Unit
  ↓
отправляет задачу
  ↓
группа имитирует ход реагирования
  ↓
чат: «выехали / прибыли / приступили / завершили»
  ↓
обучаемый сам обновляет статус ДДС
```

Чат является **учебным заменителем телефонного обмена**, а не утверждением, что реальная ДДС работает в чате.

### Два независимых состояния

Состояние виртуальной группы и статус службы в карточке не синхронизируются автоматически.

Например:

```text
ResponseAssignment = EN_ROUTE
```

не должно автоматически переводить карточку в `Начало реагирования`.
Обучаемый обязан получить сообщение, понять его смысл и выполнить правильное действие.

Это позволяет оценивать:

- правильность статуса;
- скорость реакции;
- пропущенные сообщения;
- преждевременные действия;
- инициативное уточнение обстановки.

## Маршрутизация карточки по службам

Последний ответ заказчика уточнил, что список ДДС определяется не только видом происшествия.

Учитываются как минимум:

```text
характер / признаки происшествия
+
район обслуживания
+
подчинённость объекта
→
список оповещаемых ДДС
```

Пример заказчика: при пожаре в школе района Щукино с пострадавшими информация может одновременно поступить центральным службам 01/02/03, ДДС Департамента образования, ДДС управы района и ДДС административного округа.

## Пользователи

### ADMIN

Пользователи, роли, ДДС, справочники, технические параметры.

### INSTRUCTOR

- создаёт и утверждает учебные сценарии;
- формирует занятие, подключает класс и распределяет обучаемых по группам;
- проверяет и утверждает подготовленные карточки;
- запускает и завершает смену;
- наблюдает за действиями в реальном времени и управляет паузами;
- вручную добавляет карточки и сценарные события;
- видит карточки, сообщения и временную шкалу;
- анализирует ошибки;
- подтверждает или корректирует автоматическую оценку.

### TRAINEE

- получает карточки;
- анализирует их;
- принимает решение;
- назначает виртуальную группу реагирования;
- взаимодействует с ней;
- меняет статусы и вводит комментарии;
- завершает обработку;
- получает разбор.

## Целевая учебная смена и кабинет преподавателя

Основной продуктовый источник для этого раздела — [концепция кабинета преподавателя](instructor-workspace-concept.md). Текущий базовый API занятия реализует только часть целевой модели; расширение запланировано в UT112-17—22.

```text
подготовка занятия
→ подключение класса
→ распределение обучаемых, профилей ДДС и групп
→ подготовка и утверждение карточек
→ готовность
→ запуск
→ работа с потоком карточек и live monitoring
→ завершение
→ проверка оценки преподавателем и разбор
```

`TrainingSession` охватывает всю учебную смену: настройки, участников, группы, режим, подготовленный пул сценариев, расписание выдачи, паузы, начало и завершение. `TrainingRun` — участие одного обучаемого в этой смене; в нём может быть много `Incident`. Номер АРМ и один неизменный во время активного занятия профиль ДДС относятся к `TrainingRun`, а не к постоянной учётной записи.

До запуска преподаватель может менять состав `TrainingGroup` и массово назначать профиль ДДС, сложность, категории, набор карточек и тип очереди. При запуске состав групп фиксируется как snapshot занятия. Во время смены динамическое объединение или разделение групп не предусмотрено.

Режимы: `FLOW` — автоматическая выдача в течение заданной продолжительности с интервалом (сначала фиксированным); `FIXED_SET` — заранее заданный набор; `MANUAL` — выдача преподавателем. Ручную дополнительную карточку можно отправить и в `FLOW`, и в `FIXED_SET`. Основной пул готовится до старта: преподаватель просматривает, редактирует, заменяет, перегенерирует и утверждает сценарии. Порядок `SEQUENTIAL` принят по умолчанию; `RANDOM` перемешивает только утверждённый пул, не создавая новое содержимое при выдаче.

При `INDIVIDUAL_QUEUE` карточка адресована конкретному `TrainingRun`. При `SHARED_QUEUE` новые карточки видны группе; один обучаемый атомарно берёт карточку, после чего остальные видят владельца, его АРМ и статус, сохраняя только просмотр. Преподаватель наблюдает за классом и сигналами «Требует внимания», открывает серверное состояние АРМ только для чтения. Возможные ошибки скрыты от обучаемого до разбора.

Глобальная пауза останавливает учебное время, выдачу, нормативы и сценарные события для всех; индивидуальная — для одного участника. Причина и длительность индивидуальной паузы сохраняются. Преподаватель может добавить карточку, сценарное событие или заметку, но не изменяет историю действий обучаемого от его имени. Обычное завершение `GRACEFUL` прекращает выдачу новых карточек и даёт закончить взятые; `IMMEDIATE` прекращает занятие сразу.

## TrainingScenario

Для учебных сценариев используем термин `TrainingScenario`, чтобы не путать его с техническим «сценарием реагирования» Системы-112.

```text
TrainingScenario
├── initial_incident
├── expected_result
└── timeline
    ├── карточка поступила
    ├── группа приняла задачу
    ├── группа выехала
    ├── группа прибыла
    ├── изменение обстановки
    └── работы завершены
```

На первом этапе timeline детерминированный. AI может добавляться позднее.

## Оценивание

Детерминированно проверяются:

- время;
- обязательные действия;
- правильность статусов;
- обязательность комментариев;
- наличие и фактический порядок ожидаемых этапов без искусственного запрета пропусков на уровне backend;
- реакция на сообщения группы;
- завершение сценария.

AI используется только там, где нужна семантика свободного текста, объяснение ошибок или вариативность сценариев.

Автоматическая, в том числе AI, оценка предварительна. Преподаватель подтверждает её, снимает или добавляет ошибки, меняет вес/итог и оставляет комментарий. Каждая корректировка журналируется; только после проверки формируется итоговый результат и разбор.

## Интерфейс

Заказчик просит стремиться повторить цвета и конфигурацию реального АРМ. Карточка и реестр обращений должны быть наиболее похожими; новые и второстепенные экраны могут отличаться.

## Первый vertical slice

```text
преподаватель запускает занятие
→ обучаемому поступает карточка
→ обучаемый открывает её
→ принимает
→ назначает виртуальную группу
→ отправляет задачу
→ получает сообщение группы в чате
→ вручную меняет статус карточки
→ backend сохраняет действие и время
→ преподаватель видит историю
```

Этот поток должен переживать обновление страницы и повторное подключение.

Это один ожидаемый учебный путь, а не строгая таблица допустимых backend-переходов для всех сценариев.

## Будущие учебные сценарии

Реальные ситуации подтверждены SRC-002; включение их в тренажер — `PRODUCT_DECISION`.

### Дубль карточки

Обучаемый получает несколько карточек по одному происшествию, определяет основную карточку реагирования, устанавливает корректное решение по дублю и указывает номер основной карточки в комментарии. Оценка проверяет, что действия и комментарии не создают ложное впечатление об отсутствии реагирования.

### Взаимодействие с отделом контроля реагирования

Сценарий имитирует звонок специалиста отдела контроля из-за отсутствующего/некорректного статуса, неполного комментария или спорного отказа. Обучаемый должен объяснить ситуацию, исправить доступную нетерминальную ошибку и корректно зафиксировать результат. Исправление ошибочного терминального статуса остаётся действием отдела контроля, а не скрытой возможностью обучаемого.

## Не входит в первый каркас

- реальное подключение к Системе-112;
- реальная радиосвязь;
- полноценная SIP/Asterisk-инфраструктура;
- моделирование внутренних систем каждой ДДС;
- все ведомственные исключения сразу;
- обязательный облачный AI;
- микросервисы.
