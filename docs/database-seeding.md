# Воспроизводимые данные PostgreSQL

Схема восстанавливается миграциями Alembic. Файлы `backend/seed/` хранят исходные или нормализованные данные, а команды `app.scripts.seed_*` переносят их в таблицы. Локальный data directory PostgreSQL и `pg_dump` не являются источником истины.

## Категории

- **CORE:** SRC-006, каталог служб, типы и реестр объектов, системные справочники. Эти данные обязательны для работающего MVP.
- **DEMO:** технические пользователи и виртуальная группа из `backend/seed/demo/`; после появления `ScenarioTemplate` — отобранные сценарии с устойчивым `seed_code`.
- **RUNTIME:** занятия, участия, происшествия, действия, сообщения и оценки. Их seed не затрагивает.

Каждая запись должна иметь устойчивый исходный ключ. Для demo-пользователей это `username`, для виртуальных групп — `seed_code`. Импорт обновляет изменившиеся поля и оставляет неизменные записи без записи в БД. Отсутствие записи в новом источнике не ведёт к автоматическому удалению.

## Команды

Из `backend/` после настройки `DATABASE_URL`:

```bash
uv sync
uv run alembic upgrade head
uv run python -m app.scripts.seed_demo
uv run python -m app.scripts.seed_core
uv run python -m app.scripts.seed_all
uv run python -m app.scripts.bootstrap_demo
```

`bootstrap_demo` проверяет соединение, выполняет миграции, затем CORE, DEMO и проверку целостности. Готовность выводится только после успешной проверки. `seed_demo` можно запускать отдельно.

### База с несовместимой историей миграций

Если база создавалась в старой параллельной ветке, одинаковые идентификаторы ревизий могли обозначать разные изменения схемы. Alembic не может восстановить такую историю обычной командой `upgrade head`. Для поддерживаемой старой схемы выполните из `backend/`:

```bash
uv run python -m app.scripts.reconcile_legacy_migrations
uv run python -m app.scripts.reconcile_legacy_migrations --apply
uv run python -m app.scripts.bootstrap_demo
```

Первая команда только проверяет старую схему. `--apply` работает только для распознаваемого состояния и сохраняет существующие CORE и runtime-строки. Для иных состояний она останавливается без изменений; сначала нужно сверить фактическую схему и историю миграций.

При обновлении внешнего dataset сохраняйте нормализованный файл, manifest с провайдером, ID набора, датой импорта и числом исходных строк, а также импортёр. Не сохраняйте API-ключи. Данные, которые не удаётся однозначно связать со справочником, записывайте в отчёт для ручной проверки. Каждый логический импорт должен выполняться транзакционно.

## Обмен данными через панель администратора

Раздел «Импорт данных» поддерживает экспорт и обратный импорт трёх наборов: классификатора, служб 112 и объектов Москвы. Экспорт формирует UTF-8 JSON с версионированным конвертом:

```json
{
  "format": "ut112-admin-data",
  "version": 1,
  "dataset": "services",
  "dataset_id": "services-2026-09-25",
  "exported_at": "2026-09-25T12:00:00Z",
  "records": []
}
```

Экспортированный файл можно загрузить обратно в карточку того же набора. Перед отправкой интерфейс проверяет формат, версию, раздел и наличие списка записей, а затем показывает имя файла и количество записей для подтверждения. Backend повторно валидирует структуру и выполняет импорт одной транзакцией.

Импорт использует устойчивые ключи источников, создаёт новые и обновляет существующие записи. Отсутствующие в файле записи, связи, атрибуты и теги автоматически не удаляются. Результат и ошибка сохраняются в `import_runs`, успешная операция — также в административном аудите.
