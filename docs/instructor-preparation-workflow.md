Новый подход к подготовке и проведению занятия преподавателем

**Документ:** целевая модель Instructor Preparation Workflow  
**Статус:** целевая модель для ближайшей реализации  
**Область:** кабинет преподавателя, учебные группы, библиотека сценариев, подготовка карточек, подключение АРМ  
**Рекомендуемый путь в репозитории:** `docs/instructor-preparation-workflow.md`

---

## 1. Зачем меняем текущий подход

Текущая реализация слишком сильно связывает подготовку занятия с уже подключёнными обучаемыми, `TrainingRun` и АРМ. Это не соответствует реальному процессу работы преподавателя.

Преподаватель должен иметь возможность **полностью подготовить занятие заранее**, когда:

- в учебном классе ещё никого нет;
- ни один обучаемый ещё не авторизован;
- АРМ ещё не заняты;
- `TrainingRun` ещё не созданы.

Преподаватель заранее:

1. ведёт постоянные учебные группы;
2. создаёт занятие;
3. выбирает группы, которые будут участвовать;
4. задаёт настройки для каждой группы;
5. подготавливает для каждой группы набор карточек происшествий;
6. просматривает и редактирует все карточки;
7. только в день занятия ждёт подключения обучаемых;
8. при необходимости корректирует распределение по группам;
9. запускает занятие.

Основной принцип:

> **Подготовка учебного материала не должна зависеть от фактического подключения обучаемых и наличия АРМ.**

---

# 2. Основные сущности с точки зрения пользователя

В интерфейсе преподавателя должны быть чётко разделены три понятия.

## 2.1. Постоянная учебная группа

Это группа обучаемых, которая существует между занятиями и может использоваться много раз.

Пример:

```text
Код: ДДС-101-01
Название: ДДС пожарной охраны, группа 1
Участники:
- Иванов И.И.
- Петров П.П.
- Сидоров А.А.
```

Постоянная группа отвечает на вопрос:

> **Кто эти люди?**

Она не хранит сложность конкретного урока, набор карточек или параметры конкретного занятия.

Технически для этого следует использовать существующую `UserGroup`, а не создавать параллельную сущность без необходимости.

---

## 2.2. Группа в конкретном занятии

Когда преподаватель выбирает постоянную группу для занятия, создаётся участие этой группы в конкретном уроке.

Технически это `TrainingGroup`.

Она отвечает на вопрос:

> **Что эта группа делает сегодня?**

Именно здесь хранятся настройки конкретного занятия:

- ссылка на постоянную группу;
- сложность;
- режим распределения карточек;
- подготовленный набор карточек;
- временные изменения состава только для данного занятия.

Рекомендуемая связь:

```text
UserGroup
    ↓
TrainingGroup.source_user_group_id
```

---

## 2.3. Подключившийся обучаемый

`TrainingRun` появляется только тогда, когда человек действительно подключился к занятию и занял АРМ.

Он не должен требоваться для:

- выбора групп;
- формирования карточек;
- генерации текстов;
- предварительного просмотра;
- утверждения учебного материала.

---

# 3. Структура кабинета преподавателя

В левом меню преподавателя должны быть три основных раздела:

```text
Занятия
Группы обучающихся
Библиотека сценариев
```

Позже можно отдельно добавить:

```text
Результаты
```

но это не является обязательным для текущей перестройки.

---

# 4. Раздел «Группы обучающихся»

Это самостоятельный раздел для постоянных групп.

## 4.1. Список групп

Пример:

```text
Группы обучающихся

[ + Создать группу ]

ДДС-101-01
5 человек
[Открыть]

ДДС-103-02
3 человека
[Открыть]

ДДС-102-04
6 человек
[Открыть]
```

Нужны:

- поиск;
- активные группы;
- архивные группы.

Архивные группы по умолчанию не предлагаются при создании нового занятия.

---

## 4.2. Создание группы

Минимальная форма:

```text
Название группы
[________________________]

Короткий код
[__________]

Участники
[поиск по ФИО]

Иванов И.И.   [Добавить]
Петров П.П.   [Добавить]

[Создать]
```

Рекомендуемые поля:

- `name`;
- `code`;
- `created_by_user_id`;
- `is_archived`;
- состав существующих пользователей с ролью `TRAINEE`.

Не нужно создавать пользователей из этой формы, если это усложняет MVP. Достаточно выбирать уже заведённых обучаемых.

---

## 4.3. Архивирование

Группу, которая уже использовалась в занятиях, лучше не удалять физически.

Использовать:

```text
Активна
Архив
```

Исторические занятия должны продолжать корректно отображать название и состав использованной группы.

---

# 5. Новый процесс создания занятия

Подготовка занятия делится на четыре шага:

```text
1. Параметры
        ↓
2. Группы
        ↓
3. Карточки происшествий
        ↓
4. Подключение и запуск
```

После запуска интерфейс переходит в:

```text
Live Monitor
```

После завершения:

```text
Итоги / разбор
```

---

# 6. Шаг 1 — Параметры занятия

Этот шаг должен быть максимально коротким.

## 6.1. Название

Не заставлять преподавателя придумывать название вручную.

По умолчанию формировать автоматически, например:

```text
Практическое занятие · 29.09.2026
```

или:

```text
Практическое занятие · 29.09.2026 · 10:00
```

Название можно разрешить изменить, но это не обязательное действие.

Дата создаётся автоматически.

---

## 6.2. Тема

Отдельное поле «Тема» убрать из основного UI.

Причина: одно занятие может включать смешанные группы и несколько разных сценариев.

---

## 6.3. Режим занятия

Оставить два режима.

### Потоковая тренировка

Параметры:

```text
Продолжительность
Интервал выдачи карточек
```

Карточки поступают в течение занятия.

### Набор карточек

Продолжительность не требуется.

Преподаватель заранее подготавливает конечный набор карточек для каждой группы.

Количество карточек не задаётся глобально на шаге 1. Оно определяется позже при наполнении каждой группы сценариями.

---

## 6.4. Управляемая тренировка

Текущий режим управляемой тренировки временно убрать из обычного UI.

Не обязательно удалять enum или backend-код. Достаточно не использовать режим в новом MVP workflow.

---

## 6.5. Порядок карточек

Оставить:

```text
По порядку
Случайным образом
```

Случайный порядок меняет только порядок уже подготовленных и проверенных карточек.

---

## 6.6. Рабочие места

Количество рабочих мест на шаге создания занятия не задавать.

Реальное количество определяется позже по фактически подключившимся обучаемым.

---

## 6.7. Поведение кнопки создания

После нажатия:

```text
[Создать занятие]
```

backend сохраняет черновик, а frontend **сразу переходит на шаг 2**.

Не оставлять пользователя на первом шаге с дополнительной кнопкой «Далее».

---

# 7. Шаг 2 — Группы

Этот шаг предназначен для выбора **ранее созданных постоянных групп**.

## 7.1. Выбор существующих групп

Пример:

```text
Выберите группы для занятия

☐ ДДС-101-01
   5 человек

☐ ДДС-103-02
   3 человека

☐ ДДС-102-04
   6 человек

[ + Создать новую группу ]
```

Преподаватель отмечает нужные группы.

После выбора они отображаются в блоке занятия.

---

## 7.2. Быстрое создание новой группы

Преподаватель не должен выходить из мастера занятия.

Кнопка:

```text
[ + Создать новую группу ]
```

открывает ту же минимальную форму создания постоянной группы.

После сохранения новая группа:

1. сохраняется как постоянная `UserGroup`;
2. появляется в разделе «Группы обучающихся»;
3. автоматически выбирается для текущего занятия;
4. для неё создаётся соответствующий `TrainingGroup`.

---

## 7.3. Настройки группы в занятии

Для каждой выбранной группы задать:

### Сложность

Например:

```text
Низкая
Средняя
Высокая
```

Точное внутреннее значение может оставаться числовым, но UI должен использовать понятные русские значения.

Сложность хранится в `TrainingGroup`, а не в постоянной `UserGroup`.

Одна и та же группа на разных занятиях может иметь разную сложность.

### Режим карточек

Два режима:

```text
Общий пул
Личный пул
```

---

# 8. Семантика общего и личного пула

## 8.1. Общий пул

Преподаватель подготовил для группы 12 карточек.

После старта:

```text
Группа → один общий набор из 12 карточек
```

Все участники группы видят доступные карточки.

Первый обучаемый, взявший карточку, атомарно становится её владельцем.

Существующую механику atomic claim сохранить.

---

## 8.2. Личный пул

Преподаватель подготовил для группы 12 карточек.

Если в группу на занятии подключились:

```text
Иванов
Петров
Сидоров
```

то после запуска каждый получает **полный собственный набор**:

```text
Иванов   → 12 карточек
Петров   → 12 карточек
Сидоров  → 12 карточек
```

Это не распределение 12 карточек между тремя людьми.

Каждый получает собственную независимую копию всего утверждённого набора.

---

## 8.3. Важное правило личного пула

Не нужно заново обращаться к AI и генерировать новые факты для каждого обучаемого.

Преподаватель заранее проверяет один утверждённый пакет.

При запуске личного режима система создаёт отдельные runtime-копии этого утверждённого содержания для каждого `TrainingRun`.

Таким образом:

- учебное содержание одинаковое;
- статусы независимые;
- чаты независимые;
- время независимое;
- результаты независимые.

---

# 9. Шаг 3 — Карточки происшествий

Это основной этап методической подготовки занятия.

На экране показываются все группы, выбранные на шаге 2.

Пример:

```text
ДДС-101-01
Средняя сложность
Общий пул

Подготовлено: 12 карточек

Пожар в образовательном учреждении    5
Пожар в жилом доме                    4
ДТП с пострадавшими                   3

[ + Добавить карточки по сценарию ]
```

---

# 10. Одна группа может использовать несколько сценариев

Это обязательное правило нового подхода.

Для одной группы можно подготовить набор из нескольких `ScenarioTemplate`.

Например:

```text
Template A «Пожар в школе» × 5
Template B «Пожар в доме» × 4
Template C «ДТП» × 3
```

Итого:

```text
12 карточек
```

Повторное нажатие «Добавить карточки по сценарию» не заменяет предыдущий набор, а добавляет новые карточки.

---

# 11. Выбор сценария внутри занятия

При нажатии:

```text
[ + Добавить карточки по сценарию ]
```

открывается модальное окно / drawer:

```text
Выберите сценарий

[Поиск________________]

Пожар в школе
Пожар в жилом доме
ДТП с пострадавшими
...

[ + Создать новый сценарий ]
```

Это **Scenario Picker**, а не отдельный переход в библиотеку.

Контекст уже известен:

```text
training_session_id
training_group_id
```

Поэтому внутри picker запрещено снова спрашивать:

- занятие;
- группу;
- АРМ;
- пользователя.

---

# 12. Создание сценария прямо из Scenario Picker

В окне выбора сценария есть:

```text
[ + Создать новый сценарий ]
```

Нажатие открывает тот же `ScenarioEditor`, который используется в полноценной библиотеке.

После сохранения:

```text
[Сохранить и использовать]
```

новый шаблон:

1. сохраняется в библиотеке;
2. становится доступен для будущих занятий;
3. автоматически выбирается в текущем picker;
4. преподаватель продолжает создание карточек, не теряя контекст занятия и группы.

Не создавать второй урезанный редактор.

---

# 13. Генерация карточек

После выбора шаблона преподаватель задаёт:

```text
Количество карточек: [ 5 ]

[Сформировать]
```

Для каждой карточки партии выбирается отдельный подходящий объект. Если подходящих
объектов меньше заданного количества, система сообщает об этом до создания партии.

Дополнительные параметры можно добавлять позже, но MVP не должен превращаться в технический конструктор.

---

# 14. Карточки генерируются без АРМ и TrainingRun

Это ключевое изменение backend.

Генерация должна требовать примерно:

```text
training_session_id
training_group_id
scenario_template_id
count
seed
```

Не требуется:

```text
training_run_id
workstation_number
подключённый пользователь
```

Преподаватель должен иметь возможность полностью подготовить занятие при нуле подключённых обучаемых.

---

# 15. Не создавать сложную новую Pack-архитектуру без необходимости

Для скорости рекомендуется использовать уже существующие `ScenarioInstance` как подготовленные карточки.

Минимальная целевая связь:

```text
TrainingSession
    └── TrainingGroup
          ├── ScenarioInstance
          ├── ScenarioInstance
          ├── ScenarioInstance
          └── ...
```

`ScenarioInstance` должен уметь принадлежать подготовленной группе занятия без `TrainingRun`.

При необходимости можно добавить лёгкие metadata:

- `batch_id`;
- `scenario_template_id`;
- `training_group_id`.

Не требуется создавать универсальный `PreparedCardPack` framework, если существующей модели достаточно.

---

# 16. Предпросмотр и редактирование карточек

После генерации преподаватель видит все созданные карточки.

Для каждой доступны:

```text
Открыть
Изменить условия
Перегенерировать текст
Перегенерировать карточку
Исправить текст вручную
Исключить
```

И дополнительно на уровне группы:

```text
Добавить ещё карточки
Перегенерировать тексты выбранных
```

---

## 16.1. Перегенерировать текст

Меняется только текст.

Структурированные факты остаются прежними.

---

## 16.2. Перегенерировать карточку

Могут измениться разрешённые параметры:

- объект;
- этаж;
- помещение;
- наличие пострадавших;
- другие вариативные данные шаблона.

После изменения фактов текст генерируется заново.

---

## 16.3. Ручная корректировка

Преподаватель может вручную исправить финальный текст.

Ручное изменение текста не должно менять структурированные факты карточки.

---

# 17. Библиотека сценариев как самостоятельный раздел

Раздел слева:

```text
Библиотека сценариев
```

должен быть полноценным рабочим местом, а не только picker готовых сценариев.

Вверху:

```text
[ + Создать сценарий ]
```

---

## 17.1. DRAFT

Для черновика:

```text
[Редактировать]
```

Черновики могут совместно исправлять преподаватели и администраторы согласно действующей политике проекта.

---

## 17.2. READY

READY-сценарий не редактируется на месте.

В интерфейсе пользователь видит:

```text
[Использовать]
[Изменить]
```

Кнопка «Изменить» технически:

```text
READY
→ duplicate
→ новый DRAFT
→ открыть ScenarioEditor
```

Пользователю не нужно объяснять внутреннюю механику версий.

---

## 17.3. Архивирование

READY-сценарий может архивировать:

- его автор;
- ADMIN.

Другой преподаватель не может архивировать чужой READY-сценарий.

---

# 18. Что должно быть в ScenarioEditor

Редактор сценария должен быть параметрическим и понятным преподавателю.

Пример:

```text
Название
Пожар в образовательном учреждении

Тип происшествия
Пожар

Тип объекта
Школа

Сложность по умолчанию
Средняя

Вариативные параметры
Этаж: 1–4
Помещение: кабинет / коридор / подсобка
Задымление: ...
Пострадавшие: ...

Службы
101
103 при соответствующем условии

Логика работы служб
101: следует → прибыла → выполняет работы → завершила
103: следует → прибыла → оказывает помощь → завершила
```

Преподаватель не должен вводить вручную исходный текст каждой карточки.

Он задаёт структуру и допустимые параметры.

---

# 19. Технические названия не показывать в UI

В обычном интерфейсе преподавателя запрещено показывать:

```text
SRC-006
SCHOOL
EDUCATION
GENERIC
OBJECT_BOUND
ScenarioTemplate
ScenarioInstance
RESPONSE_MESSAGE
INITIAL_REPORT
offset_seconds
EN_ROUTE
```

Вместо них:

```text
Тип происшествия
Школа
Образовательные учреждения
Любой подходящий объект
Конкретный объект
Сообщение службы
Следует к месту
```

Технические коды могут оставаться в backend, БД и диагностической админке.

---

# 20. AI: место в новой модели

AI не создаёт бизнес-логику сценария.

Правильная последовательность:

```text
ScenarioTemplate
      ↓
Variant Generator
      ↓
структурированные факты
      ↓
AI Text Renderer
      ↓
текст карточки / сообщение службы
```

AI не определяет:

- тип происшествия;
- объект;
- службы;
- количество пострадавших;
- этаж;
- правильные действия ДДС;
- итоговую оценку.

---

# 21. Стиль текста карточек

Текст должен выглядеть как быстрая рабочая запись оператора, а не как официальный отчёт или ответ чат-бота.

Пример хорошего текста:

```text
дым на 2 этаже школы, сильный запах гари, откуда идет пока не понятно
```

или:

```text
в школе дым со стороны подсобки, людей выводят
```

Избегать:

```text
Очевидец сообщает о сильном задымлении на втором этаже образовательного учреждения.
На данный момент информация о пострадавших отсутствует.
```

---

# 22. Рекомендации к prompt INCIDENT_OPERATOR_ENTRY

Основные правила:

- использовать только переданные факты;
- не добавлять обстоятельства;
- 1–3 короткие фразы;
- простой рабочий язык;
- допустим lowercase;
- допустимы неполные предложения;
- упрощённая пунктуация;
- иногда допустима одна небольшая естественная опечатка;
- не делать ошибки в каждом сообщении;
- не искажать адреса, числа, этажи, количество людей, названия объектов;
- не использовать канцеляризмы;
- вернуть только текст карточки.

Нежелательные обороты:

```text
на данный момент
наблюдается
имеется информация
очевидец сообщает о том, что
в настоящее время
```

---

# 23. Сообщения виртуальных служб

Для сообщений служб использовать отдельный AI profile.

Пример:

```text
на месте, дым со второго этажа, идем на разведку
```

```text
очаг в подсобке, начали тушение
```

```text
горение ликвидировано, проветриваем
```

Не:

```text
Пожарно-спасательное подразделение прибыло к месту происшествия.
В настоящее время проводится разведка помещений.
```

Все тексты желательно подготовить до запуска занятия.

Runtime не должен зависеть от доступности внешнего AI.

---

# 24. Шаг 4 — Подключение и запуск

Только на этом шаге появляется реальный учебный класс.

Пример:

```text
АРМ 01
Иванов И.И.
ДДС-101-01
● подключён

АРМ 02
Петров П.П.
ДДС-101-01
● подключён

АРМ 03
Смирнов А.А.
Не распределён
[Назначить группу]
```

Количество АРМ определяется фактически подключившимися пользователями.

---

# 25. Автоматическое распределение по группам

Если:

```text
User
→ UserGroup ДДС-101-01
```

и в текущем занятии есть:

```text
TrainingGroup
source_user_group_id = ДДС-101-01
```

то при подключении пользователь автоматически получает эту `TrainingGroup`.

Если его постоянная группа не участвует в занятии:

```text
Не распределён
```

---

# 26. Временное ручное изменение группы

Преподаватель может вручную назначить подключившегося обучаемого в любую группу текущего занятия.

Например обучаемый из параллельной постоянной группы пришёл на занятие другой группы.

Изменение влияет только на:

```text
TrainingRun.training_group_id
```

и не должно менять постоянную `UserGroup`.

---

# 27. Запуск занятия

Перед запуском преподаватель должен видеть:

- выбранные группы;
- количество подключённых людей;
- нераспределённых людей;
- готовность наборов карточек;
- режим пула каждой группы.

Если всё готово:

```text
[Начать занятие]
```

После этого открывается Live Monitor.

---

# 28. Материализация карточек при запуске

## Общий пул

Утверждённый пакет группы используется один раз.

```text
Approved ScenarioInstances
→ shared queue
```

Карточки забираются через atomic claim.

---

## Личный пул

Для каждого `TrainingRun` создаётся собственная runtime-копия полного утверждённого набора.

```text
Approved ScenarioInstances
      ↓
Ivanov runtime copies
Petrov runtime copies
Sidorov runtime copies
```

Не обращаться повторно к AI.

Не менять проверенные преподавателем факты.

---

# 29. Live Monitor

После старта преподаватель уже не занимается подготовкой состава и карточек.

Он наблюдает:

- АРМ;
- активные карточки;
- статусы ДДС;
- сообщения служб;
- нарушения нормативов;
- паузы;
- завершение карточек.

Существующий Live Monitor максимально переиспользовать.

---

# 30. Что не меняем

Чтобы быстро реализовать новый workflow, не нужно:

- переписывать весь Scenario Engine;
- создавать микросервисы;
- создавать новый универсальный Pack framework;
- удалять старые enum из backend;
- переписывать assessment;
- удалять старый advanced editor;
- переписывать shared queue;
- переделывать atomic claim;
- делать SIP/Asterisk;
- создавать runtime AI generation;
- выполнять большой frontend refactor.

---

# 31. Рекомендуемое минимальное техническое изменение

## UserGroup

Переиспользовать существующую сущность.

При необходимости добавить:

```text
code
created_by_user_id
is_archived
```

---

## TrainingGroup

Добавить / использовать:

```text
source_user_group_id
difficulty
queue_mode
```

`queue_mode`:

```text
SHARED_QUEUE
INDIVIDUAL_QUEUE
```

---

## ScenarioInstance

Разрешить подготовленный экземпляр сценария привязывать к:

```text
training_session_id
training_group_id
```

без обязательного `training_run_id`.

Подготовленные экземпляры существуют до подключения АРМ.

---

## TrainingRun

Создаётся только при реальном подключении пользователя.

При создании:

1. определить постоянную `UserGroup`;
2. найти соответствующий `TrainingGroup` текущего занятия;
3. автоматически назначить её;
4. если соответствия нет — оставить пользователя нераспределённым.

Преподаватель может изменить назначение только в рамках занятия.

# 32. Рекомендуемое разбиение реализации

Критерий готовности:

## UT112-42.3 — Карточки происшествий по группам без АРМ

- предварительный просмотр;
- редактирование условий;

- исключение;
- утверждение подготовленного набора.

Критерий готовности:

## UT112-42.4 — Подключение, автоматическое распределение и запуск

Сделать:

- показывать нераспределённых;
- дать преподавателю временно поменять группу;
- общий пул использовать один раз;
- при личном пуле клонировать полный утверждённый набор каждому TrainingRun;
- запуск занятия после проверки состава.

Критерий готовности:

> После подключения людей преподавателю остаётся только исправить исключения и нажать «Начать занятие».

# 33. Основной acceptance flow

Полный обязательный сценарий проверки:

```text
INSTRUCTOR
↓
создаёт постоянную группу A
↓
создаёт постоянную группу B
↓
создаёт новое занятие
↓
сразу переходит на шаг «Группы»
↓
выбирает A и B
↓
A: Средняя / Общий пул
B: Высокая / Личный пул
↓
переходит к карточкам
↓
A:
  Пожар в школе × 5
  ДТП × 3
↓
B:
  Медицинское происшествие × 4
  ДТП × 2
↓
карточки создаются без подключённых пользователей
↓
преподаватель просматривает, исправляет и утверждает наборы
↓
обучаемые входят на АРМ
↓
автоматически распределяются по постоянным группам
↓
одного обучаемого преподаватель вручную переносит в другую группу только на это занятие
↓
запуск
↓
группа A получает один общий пул
↓
группа B: каждый участник получает полный личный набор
↓
Live Monitor
↓
работа с карточками и виртуальными службами
↓
завершение
↓
итоговый разбор
```

---

# 34. Ключевые продуктовые правила

1. Занятие можно полностью подготовить до прихода обучаемых.
2. Постоянные группы используются повторно в разных занятиях.
3. Настройки сложности и пула принадлежат группе конкретного занятия.
4. Одна группа может получать карточки из нескольких шаблонов сценариев.
5. Общий пул — один набор на всю группу.
6. Личный пул — полный собственный набор каждому обучаемому.
7. Карточки создаются и проверяются до существования `TrainingRun`.
8. Встроенный Scenario Picker не спрашивает повторно занятие или группу.
9. Новый сценарий можно создать прямо из Scenario Picker.
10. Самостоятельная библиотека сценариев остаётся полноценным редактором.
11. READY-сценарий не редактируется на месте; создаётся редактируемая DRAFT-версия.
12. Архивировать READY может автор или ADMIN.
13. AI формулирует текст, но не определяет бизнес-факты.
14. Подготовленные AI-тексты сохраняются до занятия.
15. Состояние виртуальной группы не меняет статус ДДС автоматически.
16. Технические названия и enum-коды не показываются преподавателю.
17. Приоритет — простой рабочий путь преподавателя, а не универсальность архитектуры.

---

# 35. Короткая формула нового подхода

```text
Постоянные группы
        +
Библиотека сценариев
        ↓
Создание занятия
        ↓
Выбор групп
        ↓
Настройка сложности и режима пула
        ↓
Подготовка карточек каждой группе из нескольких сценариев
        ↓
Предварительная проверка всего материала
        ↓
Подключение обучаемых
        ↓
Автоматическое распределение по группам
        ↓
Ручная корректировка исключений
        ↓
Запуск
        ↓
Live Monitor
        ↓
Разбор результатов
```

Это является целевым Instructor Preparation Workflow для ближайшей реализации и должно использоваться как основной продуктовый источник при выполнении задач `UT112-42.1`–`UT112-42.4`.
