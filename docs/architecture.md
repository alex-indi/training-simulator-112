## Основные модули

### incidents

Учебные карточки, статусы ДДС, комментарии, `available_actions`, история действий.

### response

Виртуальные группы реагирования и их назначения.

Предварительные сущности:

```text
ResponseUnit
ResponseAssignment
ResponseMessage
```

`ResponseUnit` описывает идентичность виртуальной группы. Runtime-состояние конкретного выезда хранится в `ResponseAssignment` и не является статусом карточки.

### virtual112

Имитация внешней для ДДС части Системы-112:

- формирование готовой учебной карточки;
- доставка карточки;
- имитация внешних изменений и других служб;
- позднее — маршрутизация через классификатор/территорию/подчинённость.

### training

Целевая модель кабинета преподавателя определяется [концепцией учебной смены](instructor-workspace-concept.md). Базовый код UT112-6—9 пока реализует только часть модели.

```text
TrainingSession (всё занятие)
├── настройки режима, длительности и выдачи
├── TrainingGroup[] (состав фиксируется при старте)
├── ScenarioQueue[] → ScenarioQueueItem[] → TrainingScenario
├── интервалы глобальных пауз и session control
└── TrainingRun[] (один обучаемый на всю смену)
    ├── User, workstation_number, dds_profile, difficulty, group
    ├── интервалы индивидуальных пауз
    ├── Incident[]
    └── InstructorNote[]
```

`TrainingScenarioEvent` задаёт события подготовленного сценария. `TrainingRun` не создаётся на каждую карточку: участник может обработать много `Incident` за смену. Номер АРМ и профиль ДДС назначаются участию; профиль не меняется после старта. `TrainingGroup` хранит массовые настройки и snapshot состава на момент старта.

`ScenarioQueue` — очередь утверждённых до запуска сценариев для участника или группы. Режимы `FLOW`, `FIXED_SET`, `MANUAL` и порядок `SEQUENTIAL` (default) / `RANDOM` принадлежат настройкам конкретной `TrainingSession`. `FLOW` задаёт продолжительность и интервал выдачи; формат расписания должен допускать будущий случайный диапазон интервалов. `RANDOM` выбирает порядок уже подготовленных элементов, не генерирует новый контент. Ручная дополнительная выдача доступна в любом режиме.

Текущая реализация UT112-18 хранит пул в `ScenarioQueueItem`, привязанном к `TrainingRun`. Редактирование или замена создаёт новую версию `TrainingScenario` и снимает утверждение позиции. При запуске сервер фиксирует `delivery_position` отдельно для каждого АРМ. `FLOW` выдаёт по одной карточке на АРМ в каждый интервал учебного времени; `FIXED_SET` выдаёт весь набор при запуске; `MANUAL` не запускает автоматическую выдачу. Scheduler читает БД каждые секунду и блокирует строку `TrainingSession` на время выдачи, поэтому повторный тик не создаёт вторую карточку. В `Incident.source_snapshot` копируется подготовленное содержимое; изменение источника не меняет выданную карточку. `delivery_elapsed_seconds` и `delivery_checked_at` оставляют точку расширения для пауз UT112-21. Групповая и общая очередь остаются участком UT112-19; запуск с `SHARED_QUEUE` пока блокируется проверкой готовности.

Socket.IO сообщает `incident.delivered` только участникам занятия. Клиент после события и reconnect перечитывает REST; для текущего локального стенда сервер запускается одним ASGI process через `app.main:socket_app`.

`INDIVIDUAL_QUEUE` выдаёт карточку конкретному `TrainingRun`. `SHARED_QUEUE` выдаёт её группе: до claim карточка доступна всем её участникам только как новая, после claim владелец получает право редактирования, а остальные видят статус, владельца и АРМ. Захват реализуется в UT112-19 одной транзакционной условной операцией или эквивалентной блокировкой: запись `claimed_by_training_run`, `claimed_at` и `workstation_number` делается атомарно, повторный конкурентный захват отклоняется. Доступ к `Incident` и изменениям ДДС проверяется по владельцу.

Команды преподавателя — ручная карточка, сценарное событие, глобальная или личная пауза, resume, завершение, заметка — отдельны от действий обучаемого. `InstructorNote` привязана к `TrainingRun`, имеет автора и серверное время, скрыта во время занятия и используется при разборе. Преподаватель видит read-only состояние АРМ; подмена `IncidentAction` от имени обучаемого запрещена.

`TrainingSession` управляет глобальным учебным временем; `TrainingRun` — личными нормативами и выдачей. Глобальная пауза останавливает выдачу и сценарные события всем, личная — одному участнику. Расчёт учебных дедлайнов вычитает длительность объединения глобальных и личных пауз без двойного учёта пересечений. После `GRACEFUL` новые карточки не выдаются, уже взятые можно закончить; `IMMEDIATE` прекращает занятие сразу. Подробные переходы приведены в [state machines](state-machines.md).

### assessment

Детерминированные и AI-проверки создают предварительный результат и сигналы для преподавателя. Окончательный результат появляется после `instructor review`: подтверждения, снятия/добавления ошибки, правки оценки или комментария. Каждое изменение оценки журналируется с автором, серверным временем и прежним/новым значением; обучаемый получает итог после разбора, а не подсказки об ошибках во время работы.

### План эволюции существующей схемы

Схема UT112-6—9 хранит участников в `training_session_trainees`, а `Incident` ссылается только на `training_session_id`. `TrainingRun`, группы, очереди, паузы и связь карточки с владельцем ещё отсутствуют. Это требует **новых добавочных миграций** в UT112-17—22, без переписывания старых ревизий:

1. В UT112-17 создать `TrainingRun` с уникальным участием пользователя в занятии, назначением АРМ и профиля ДДС; перенести существующие пары из `training_session_trainees`, сохранив текущий API на переходный период. Добавить `TrainingGroup` и snapshot назначения.
2. В UT112-18 добавить настройки режима/порядка, `ScenarioQueue`/`ScenarioQueueItem`, расписание и журнал выдачи. В UT112-19 добавить групповую адресацию, владельца и атомарный claim карточки.
3. Связать существующие `Incident` с `TrainingRun` только там, где владелец достоверно установлен. Текущая схема не хранит его явно: по одному `training_session_id` нельзя безопасно угадать владельца для занятий с несколькими обучаемыми. До проверки/ручного разрешения таких данных допускается временно nullable ссылка; ограничение ужесточить после backfill. Общие карточки остаются без владельца до claim.
4. В UT112-21 добавить интервалы пауз, журнал команд преподавателя и заметки; в UT112-22 — версионируемый результат оценивания и аудит правок. Изменения `ResponseUnit` / `ResponseAssignment` из параллельной UT112-10 не затрагивать.

Переходные endpoint должны читать старые данные без потери карточек; новые права доступа включать после появления проверенной связи с `TrainingRun`.

## Почему TrainingScenario, а не Scenario

В исходной системе термин «сценарий реагирования» уже используется как техническое понятие. Чтобы избежать неоднозначности, учебные сценарии продукта именуются `TrainingScenario`.

## Двойное состояние реагирования

Ключевое архитектурное правило:

```text
ResponseAssignment state Incident/DDS status
------------------      -------------------
EN_ROUTE                может всё ещё быть ACCEPTED
ARRIVED                 обучаемый должен сам выбрать ARRIVAL
WORKING                 обучаемый должен сам выбрать WORK_IN_PROGRESS
COMPLETED               обучаемый должен сам завершить карточку
```

Изменение состояния `ResponseAssignment` создаёт сообщение/событие, но не выполняет доменную команду от имени обучаемого.

## Чат виртуальной группы

Первый MVP использует текстовый realtime-канал, который имитирует телефонную коммуникацию.

Сообщения хранятся в БД и доставляются через Socket.IO.

```text
ResponseMessage
- id
- response_assignment_id
- sender_type: DISPATCHER | RESPONSE_UNIT | SYSTEM
- body
- created_at
```

REST остаётся каноническим источником истории. Socket.IO только уведомляет о новом сообщении.

## Поведение виртуальной группы

Первый вариант — детерминированный движок на основе `TrainingScenarioEvent`.

Пример:

```text
+00:20 ACKNOWLEDGED
+01:00 EN_ROUTE
+04:00 ARRIVED
+05:00 WORKING
+10:00 COMPLETED
```

Событие может:

- изменить состояние `ResponseAssignment`;
- создать сообщение от старшего группы;
- ожидать инициативного запроса обучаемого;
- добавить осложнение.

AI не нужен для первого vertical slice.

## Маршрутизация

Будущий `RoutingEngine` должен позволять учитывать:

```text
classification
+
service area
+
object affiliation
→ notification targets
```

Не реализовывать полный routing до отдельной задачи. Первый MVP может использовать заранее подготовленный список оповещения в `TrainingScenario`.

## Workflow карточки

Backend — единственный источник правил.

Предполагаемое расположение:

```text
backend/app/modules/incidents/workflow.py
```

Ответ API включает `available_actions`.

Точная универсальная state machine не должна зашиваться в frontend.

## История действий

`IncidentAction` хранит минимум:

```text
CARD_OPENED
PRIMARY_STATUS_CHANGED
COMMENT_ADDED
RESPONSE_UNIT_ASSIGNED
RESPONSE_TASK_SENT
RESPONSE_MESSAGE_READ
STATUS_CHANGED
CARD_COMPLETED
```

Оценивание строится на хронологии действий и событий.

## REST и realtime

REST:

- текущее состояние;
- команды пользователя;
- восстановление после reconnect;
- история сообщений и действий.

Socket.IO:

```text
incident.delivered
incident.updated
response.message_created
response.state_changed
session.started
session.paused
session.resumed
session.finished
run.paused
run.resumed
incident.claimed
assessment.completed
```

После reconnect frontend обязательно повторно запрашивает server state.

## Время

Backend/PostgreSQL — UTC. API — ISO 8601.

Для карточки отдельно хранить:

```text
delivered_at
opened_at
primary_status_at
```

Для `ResponseAssignment` и сообщений — серверные временные метки. Паузы, выдача, claim, заметки и правки оценки также получают серверные метки; учебное время рассчитывается с исключением пауз.

## Оценивание

Детерминированная часть сравнивает фактический мир сценария с действиями обучаемого.

Пример:

```text
ResponseAssignment EN_ROUTE at 14:04:00
Trainee set START_RESPONSE at 14:04:18
reaction_delay = 18 seconds
```

Это позволяет оценивать несвоевременные и неправильные действия без AI.

## Интеграции

```text
AIProvider
TelephonyProvider
ClassifierImporter
```

Чат не должен быть жёстко связан с телефонией. Позднее `TelephonyProvider` сможет заменить или дополнить учебный канал без переделки `ResponseAssignment` и `ResponseUnit`.

## Локальная разработка

До первого полного Compose:

```text
PostgreSQL → Docker
Backend → local hot reload
Frontend → Vite dev server
```

Контрольный воспроизводимый запуск позднее:

```text
docker compose up --build
```

## Непрерывность разработки

Состояние проекта хранится в Git:

- долговременные знания — `docs/`;
- состояние `main` — `docs/current-state.md`;
- состояние активной ветки — `tasks/UT112-xxx.md`;

## Не добавлять без отдельного решения

- микросервисы;
- Redis;
- Kafka/RabbitMQ;
- Celery;
- Kubernetes;
- обязательный cloud AI;
- полноценную SIP-инфраструктуру;
- отдельный workflow для каждой реальной ДДС в первом MVP.
