## Основные модули

### Object Registry Layer

```text
Open Data Sources → Object Registry → Scenario Generator → Training Incident
```

`object_registry` хранит типы объектов как дерево записей БД, конкретные объекты с происхождением данных, свободные атрибуты и поисковые теги. Запросы по типу охватывают потомков; запросы по тегам помогают подобрать место для будущего сценария. Реестр не связывает объекты напрямую с происшествиями или службами. Схема и границы описаны в [документе реестра](object-registry.md).

### incidents

Учебные карточки, статусы ДДС, комментарии, `available_actions`, история действий.

### response

Виртуальные группы реагирования и их назначения.

Реализованные сущности:

```text
ResponseUnit
ResponseAssignment
```

`ResponseMessage` и чат реализуются отдельно от стабилизации текущей модели.

`ResponseUnit` описывает идентичность виртуальной группы. Runtime-состояние конкретного выезда хранится в `ResponseAssignment` и не является статусом карточки.

### virtual112

Имитация внешней для ДДС части Системы-112:

- формирование готовой учебной карточки;
- доставка карточки;
- имитация внешних изменений и других служб;
- позднее — маршрутизация через классификатор/территорию/подчинённость.

### training

Целевая модель кабинета преподавателя определяется [концепцией учебной смены](instructor-workspace-concept.md). UT112-17–19 реализовали подготовку занятия, очереди и общий claim; ветки UT112-20–22 добавляют монитор, управление и разбор.

```text
TrainingSession (всё занятие)
├── настройки режима, длительности и выдачи
├── TrainingGroup[] (состав фиксируется при старте)
├── ScenarioQueueItem[] → TrainingScenario
└── TrainingRun[] (один обучаемый на всю смену)
    ├── User, workstation_number, dds_profile, difficulty, group
    ├── Incident[]
```

`TrainingScenarioEvent` задаёт события подготовленного сценария. `TrainingRun` не создаётся на каждую карточку: участник может обработать много `Incident` за смену. Номер АРМ и профиль ДДС назначаются участию; профиль не меняется после старта. `TrainingGroup` хранит массовые настройки и snapshot состава на момент старта.

`ScenarioQueueItem` — позиция очереди для участника или группы. Режимы `FLOW`, `FIXED_SET`, `MANUAL` и порядок `SEQUENTIAL` / `RANDOM` принадлежат `TrainingSession`. Для `FIXED_SET` требуется хотя бы одна утверждённая карточка на каждый target. `RANDOM` меняет порядок уже подготовленных элементов.

Пул хранится в `ScenarioQueueItem`, адресованном одному `TrainingRun` или `TrainingGroup`. Редактирование или замена создаёт новую версию `TrainingScenario` и снимает утверждение позиции. При запуске сервер фиксирует `delivery_position` отдельно для каждого АРМ или группы. `FLOW` выдаёт по одной карточке на адресата в каждый интервал учебного времени; `FIXED_SET` выдаёт весь набор при запуске; `MANUAL` не запускает автоматическую выдачу. Scheduler читает БД каждую секунду и блокирует строку `TrainingSession` на время выдачи, поэтому повторный тик не создаёт вторую карточку. В `Incident.source_snapshot` копируется подготовленное содержимое; изменение источника не меняет выданную карточку. `delivery_elapsed_seconds` и `delivery_checked_at` хранят накопленное учебное время; интервалы `SessionPause` и `RunPause` вычитаются из нормативов и индивидуального расписания без двойного учёта пересечений.

Socket.IO сообщает участникам занятия о доставке, открытии, claim, статусах ДДС и изменениях виртуальной группы. Событие содержит только `session_id` и `incident_id`; клиент после события и reconnect перечитывает REST. Сервер запускается одним ASGI process через `app.main:socket_app`.

`INDIVIDUAL_QUEUE` выдаёт карточку конкретному `TrainingRun`. `SHARED_QUEUE` выдаёт её группе: до claim карточка доступна всем её участникам только как новая, после claim владелец получает право редактирования, а остальные видят статус, владельца и АРМ. Захват использует условный `UPDATE ... WHERE claimed_by_training_run_id IS NULL`; в одной операции записываются `claimed_by_training_run_id`, `claimed_at` и ссылка `training_run_id`. Повторный конкурентный захват получает 409. Номер АРМ и ФИО читаются из `TrainingRun` и `User`, без дублирования в карточке. После claim и изменения статуса Socket.IO уведомляет всю сессию; клиент перечитывает REST. Доступ к `Incident` проверяется по группе, право изменения — по владельцу.

Команды преподавателя — ручная карточка, сценарное событие, глобальная или личная пауза, resume, завершение, заметка — отдельны от действий обучаемого. REST-команды сохраняют `InstructorAction` с автором и серверным временем. Ручная карточка копирует утверждённый сценарий занятия в отдельный `Incident`; `ScenarioEvent` добавляет вводную к существующей карточке, сохраняя исходный snapshot и историю действий. `InstructorNote` привязана к `TrainingRun`, имеет автора и серверное время, скрыта во время занятия и доступна преподавателю для итогового разбора. Преподаватель видит read-only состояние АРМ; подмена `IncidentAction` от имени обучаемого запрещена.

`TrainingSession` управляет глобальным учебным временем; `TrainingRun` — личными нормативами и выдачей. Глобальная пауза останавливает выдачу и сценарные события всем, личная — одному участнику. Расчёт учебных дедлайнов вычитает длительность объединения глобальных и личных пауз без двойного учёта пересечений. После `GRACEFUL` новые карточки не выдаются, уже взятые можно закончить; `IMMEDIATE` прекращает занятие сразу. Подробные переходы приведены в [state machines](state-machines.md).

### assessment

После `TrainingSession.COMPLETED` первый запрос разбора фиксирует `AssessmentResult` для каждого `TrainingRun`: неизменяемую `automatic_score`, версию правил, метрики и `AssessmentDeviation`. Правила v1 проверяют 30-секундную первичную реакцию по учебному времени (с исключением пауз), отсутствие первичного решения и завершения, возможный отказ, обязательный комментарий, пропущенные/переставленные статусы и сообщения группы реагирования. Предварительная оценка равна `max(0, 100 − сумма весов сигналов)`; она не является окончательной оценкой. Спорный отказ показывается как сигнал преподавателю, а не как установленная ошибка. Семантика свободного текста и AI не требуются для работы экрана.

Преподаватель подтверждает или снимает каждый сигнал, может добавить замечание, изменить итоговый балл и написать комментарий. `AssessmentAudit` сохраняет автора, серверное время, причину и состояние до/после каждого решения. Подтверждение итога требует рассмотрения всех сигналов. Исходный автоматический балл не меняется. Обучаемый видит только подтверждённый итог завершённого занятия; история содержит дату, занятие, профиль ДДС, сложность, количество карточек и итог.

### Дальнейшие миграции

Миграции UT112-17–19 добавили `TrainingRun`, группы, очереди и nullable-связь карточки с владельцем. Старые карточки без достоверного владельца сохраняются. Миграции UT112-21/22 добавляют паузы, заметки и оценку; старые ревизии не переписываются.

## Почему TrainingScenario, а не Scenario

В исходной системе термин «сценарий реагирования» уже используется как техническое понятие. Чтобы избежать неоднозначности, учебные сценарии продукта именуются `TrainingScenario`.

## Scenario Library & Generator

[docs/scenario-library-and-generator.md](scenario-library-and-generator.md) описывает предметную архитектуру будущего модуля библиотеки и генерации учебных сценариев: источники данных, шаблон, экземпляр занятия и выдаваемый `Incident`. Это целевая концепция, а не описание уже реализованного отдельного модуля.

## Incident Classification Layer

```text
SRC-006 → Classifier Rules → Features → Incident Type → Dispatch Services
```

`IncidentClassifierRule` хранит отдельную строку SRC-006, включая код, группу, итоговый тип, тип ЕКП-35 и ссылку на лист/строку Excel. `IncidentFeature` хранит исходное значение и колонку признака; связь многие-ко-многим позволяет повторно использовать признак. `DispatchService` содержит официальное имя и ссылку на скриншот каталога заказчика. `IncidentRuleService` хранит только подтверждённую источником рекомендацию, в том числе ссылку на ячейку Excel. Неоднозначные соответствия остаются без связи до проверки человеком.

Будущие `ScenarioTemplate`, `ScenarioInstance` и `ScenarioEvent` смогут ссылаться на правило и выбранные службы без изменения классификатора. Выданный `Incident` сохранит собственный snapshot подготовленного экземпляра; текущая логика карточки этой задачей не меняется.

## Двойное состояние реагирования

Ключевое архитектурное правило:

```text
ResponseAssignment state Incident/DDS status
------------------      -------------------
EN_ROUTE                может всё ещё быть ACCEPTED
ARRIVED                 обучаемый должен сам выбрать ARRIVAL
WORKING                 обучаемый должен сам выбрать WORK_IN_PROGRESS
COMPLETED               обучаемый должен сам завершить карточку
```

Изменение состояния `ResponseAssignment` создаёт запись истории и realtime-уведомление, но не выполняет доменную команду от имени обучаемого. Сообщения чата относятся к отдельной реализации.

## Чат виртуальной группы

Первый MVP использует текстовый realtime-канал, который имитирует телефонную коммуникацию.

Сообщения хранятся в БД и доставляются через Socket.IO.

```text
ResponseMessage
- id
- response_assignment_id
- sender_type: DISPATCHER | RESPONSE_UNIT | SYSTEM
- body
- created_at
```

REST остаётся каноническим источником истории. Socket.IO только уведомляет о новом сообщении.

## Поведение виртуальной группы

Первый вариант — детерминированный движок на основе `TrainingScenarioEvent`.

Пример:

```text
+00:20 ACKNOWLEDGED
+01:00 EN_ROUTE
+04:00 ARRIVED
+05:00 WORKING
+10:00 COMPLETED
```

Событие может:

- изменить состояние `ResponseAssignment`;
- создать сообщение от старшего группы;
- ожидать инициативного запроса обучаемого;
- добавить осложнение.

AI не нужен для первого vertical slice.

## Маршрутизация

Будущий `RoutingEngine` должен позволять учитывать:

```text
classification
+
service area
+
object affiliation
→ notification targets
```

Не реализовывать полный routing до отдельной задачи. Первый MVP может использовать заранее подготовленный список оповещения в `TrainingScenario`.

## Workflow карточки

Backend — единственный источник правил.

Предполагаемое расположение:

```text
backend/app/modules/incidents/workflow.py
```

Ответ API включает `available_actions`.

Точная универсальная state machine не должна зашиваться в frontend.

## История действий

`IncidentAction` хранит минимум:

```text
CARD_OPENED
PRIMARY_STATUS_CHANGED
COMMENT_ADDED
RESPONSE_UNIT_ASSIGNED
RESPONSE_TASK_SENT
RESPONSE_MESSAGE_READ
STATUS_CHANGED
CARD_COMPLETED
```

Оценивание строится на хронологии действий и событий.

## REST и realtime

REST:

- текущее состояние;
- команды пользователя;
- восстановление после reconnect;
- история сообщений и действий.

Socket.IO:

```text
incident.delivered
incident.updated
response.message_created
response.state_changed
session.started
session.paused
session.resumed
session.finished
run.paused
run.resumed
incident.claimed
assessment.completed
```

После reconnect frontend обязательно повторно запрашивает server state.

## Время

Backend/PostgreSQL — UTC. API — ISO 8601.

Для карточки отдельно хранить:

```text
delivered_at
opened_at
primary_status_at
```

Для `ResponseAssignment` и сообщений — серверные временные метки. Паузы, выдача, claim, заметки и правки оценки также получают серверные метки; учебное время рассчитывается с исключением пауз.

## Оценивание

Детерминированная часть сравнивает фактический мир сценария с действиями обучаемого.

Пример:

```text
ResponseAssignment EN_ROUTE at 14:04:00
Trainee set START_RESPONSE at 14:04:18
reaction_delay = 18 seconds
```

Это позволяет оценивать несвоевременные и неправильные действия без AI.

## Интеграции

```text
AIProvider
TelephonyProvider
ClassifierImporter
```

Чат не должен быть жёстко связан с телефонией. Позднее `TelephonyProvider` сможет заменить или дополнить учебный канал без переделки `ResponseAssignment` и `ResponseUnit`.

## Локальная разработка

Схема PostgreSQL задаётся миграциями Alembic. Обязательные справочники и демонстрационный контент должны восстанавливаться из версионированных файлов `backend/seed/` через идемпотентные импортёры. Runtime-история занятий остаётся локальной. Одна точка входа `app.scripts.bootstrap_demo` объединяет миграции, CORE/DEMO импорт и проверку целостности; детали и текущие зависимости описаны в [database-seeding.md](database-seeding.md).

Сейчас локальный запуск:

```text
PostgreSQL → локальный сервер
Backend → local hot reload
Frontend → Vite dev server
```

Compose остаётся возможным будущим способом воспроизводимого запуска, но пока не реализован.

Возможная команда после его реализации:

```text
docker compose up --build
```
