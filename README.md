# Учебный тренажёр 112

Тренажёр для подготовки диспетчеров ДДС к работе с карточками происшествий Системы-112.

Актуальная архитектура и ограничения зафиксированы в [`docs/current-state.md`](docs/current-state.md).

## Что делает MVP

Основной продуктовый поток:

```text
Шаблон инцидента → несколько карточек → предварительный просмотр →
сохранение в библиотеку или добавление в занятие → общий/личный пул →
обучаемый берёт карточку → принимает/отклоняет → получает сообщения служб →
вручную меняет статусы ДДС → завершает карточку → автоматический разбор →
преподаватель подтверждает итог
```

Преподаватель заранее создаёт занятие, выбирает группы и готовит набор карточек происшествий. Карточки формируются из методических шаблонов на реальных объектах Москвы. В шаблоне хранятся тип происшествия, тип объекта, сложность и варианты фактов; он не задаёт универсальный алгоритм действий ДДС. Классификация, службы, объект и бизнес-логика определяются проверенными данными и правилами backend. AI может сформулировать текст карточки, но не принимает бизнес-решения.

Во время занятия обучаемый занимает АРМ, получает карточку, принимает или отклоняет её и вручную ведёт статусы своей ДДС. После принятия карточки тренажёр выдаёт сообщения других служб и учебной бригады 101. Эти сообщения не меняют статус ДДС автоматически: обучаемый сам фиксирует `Начало реагирования → Прибытие → Проведение работ → Работы завершены`.

Общий пул — основной режим MVP: карточка видна группе, но первый claim атомарно закрепляет её за одним обучаемым. Личный пул также поддерживается. После занятия преподаватель получает рассчитанный по истории разбор; AI может написать только текстовое резюме. Итоговую оценку подтверждает преподаватель.

## Стек

- Backend: Python 3.12, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 16, python-socketio.
- Frontend: React 19, Vite 7, JavaScript, CSS Modules.
- REST хранит каноническое состояние; Socket.IO сообщает клиентам об изменениях.
- AI: provider-agnostic `AITextRenderer` с OpenAI/OpenAI-compatible provider и детерминированным fallback.

## Первый запуск

Требования: Python 3.12+, `uv`, Node.js 22+ и PostgreSQL 16+.

Создайте локальную БД `training_simulator_112`, скопируйте `.env.example` в `.env` и при необходимости измените `DATABASE_URL`.

Из корня репозитория:

macOS / Linux:

```bash
python3 dev.py
```

Windows:

```powershell
py dev.py
```

`dev.py` синхронизирует зависимости, выполняет `alembic upgrade head`, проверяет PostgreSQL и запускает backend/frontend. По умолчанию:

- frontend: `http://127.0.0.1:5173`;
- backend: `http://127.0.0.1:8000`;
- health: `http://127.0.0.1:8000/health`;
- OpenAPI: `http://127.0.0.1:8000/docs`.

Для первичного наполнения чистой БД можно отдельно выполнить:

```bash
cd backend
uv sync
uv run python -m app.scripts.bootstrap_demo
uv run python -m app.scripts.seed_all
```

Seed восстанавливает классификатор, каталог служб, Object Registry, московские объекты, demo-пользователей и данные демонстрационных шаблонов.

## Запуск в учебном классе по LAN

В корневом `.env` задайте адрес сервера, например:

```env
BACKEND_HOST=0.0.0.0
FRONTEND_HOST=0.0.0.0
BACKEND_PORT=8000
FRONTEND_PORT=5173
VITE_API_URL=http://192.168.1.25:8000
FRONTEND_ORIGINS=http://192.168.1.25:5173
```

После запуска откройте на клиентском компьютере `http://192.168.1.25:5173`.

Для MVP запускайте один backend worker/process. Планировщик доставки дополнительно защищён PostgreSQL advisory lock, но это не режим работы нескольких backend-процессов для учебного стенда.

## Рабочий путь преподавателя

Подготовка занятия состоит из четырёх шагов:

1. **Параметры занятия** — режим, длительность, интервал и порядок выдачи.
2. **Группы** — постоянные группы, сложность и общий/личный пул.
3. **Карточки происшествий** — сформировать набор из шаблона или добавить готовые карточки из библиотеки; проверить объект, адрес, условия и текст; перегенерировать или исключить отдельную карточку.
4. **Подключение и запуск** — дождаться АРМ, проверить распределение по группам и начать занятие.

Обычный преподаватель работает с объектом, адресом, условиями и текстом карточки: может изменить условия, исправить или перегенерировать текст, перегенерировать карточку, сохранить её в библиотеку либо исключить. Набор можно просмотреть, перегенерировать и добавить в занятие. Работа бригады 101 и первичные реакции других служб формируются backend во время занятия; их отдельного конструктора в MVP нет.

## Рабочий путь ДДС

1. Получить карточку из личного или общего пула.
2. Для общего пула взять карточку в работу.
3. Открыть карточку и поставить первичное решение `Принята` или `Не принята`.
4. После принятия следить за сообщениями служб и бригады 101.
5. Самостоятельно менять статусы ДДС по фактической обстановке.
6. Завершить карточку.

Состояние виртуальной бригады и статус ДДС независимы. Бригада 101 проходит этапы выезда, прибытия, работ и завершения по учебному времени с учётом пауз. Другие службы отвечают только если они указаны в snapshot карточки; по умолчанию они принимают карточку, результат не зависит от ID инцидента.

## Demo-аутентификация

Локальный стенд использует demo-пользователей и `X-Demo-User`. Это сознательный механизм хакатонного/учебного стенда, а не production authentication.

## Проверки

Backend:

```bash
cd backend
uv run ruff check .
uv run pytest -q
```

Frontend:

```bash
cd frontend
npm ci
npm run lint
npm run build
```

MVP Playwright smoke на отдельной тестовой PostgreSQL:

```bash
npm run test:e2e:mvp
```

Для Playwright должны быть явно заданы `E2E_BASE_URL` и `E2E_API_URL`. Тестовая БД должна быть изолирована от рабочей.

Полный набор старых E2E-сценариев остаётся доступен через:

```bash
npm run test:e2e
```

## Работа двух разработчиков

Минимальный процесс:

```text
WEEEK говорит, что делать.
Git хранит работу.
Codex помогает продолжить с того же места.
```

Перед началом задачи обновите `main`, создайте отдельную ветку и не смешивайте несколько задач в одном PR. После выполнения проверьте backend lint/tests, frontend lint/build и соответствующий E2E smoke.

## Что сознательно не входит в MVP

- промышленная auth-схема;
- SIP/Asterisk;
- прямая интеграция с промышленной Системой-112;
- генерация бизнес-фактов LLM во время занятия;
- Redis/Celery/Kafka и микросервисы;
- конструктор timeline, сообщений служб, универсальных ожидаемых действий ДДС и критериев сценария для преподавателя. Старый Scenario Engine сохранён в backend как legacy/internal, но не является пользовательским MVP workflow.
