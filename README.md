# Учебный тренажер 112

Учебный тренажер для подготовки диспетчеров дежурно-диспетчерских служб (ДДС) к работе с карточками происшествий, поступающими из Системы-112.

Основной обучаемый — **диспетчер ДДС**. Он получает уже сформированную карточку, анализирует её, принимает решение о реагировании своей службы, взаимодействует с группой реагирования и ведёт статусы и комментарии.

> **Главный принцип разработки:** Git-репозиторий — память проекта. Codex-чат — временный рабочий контекст.

Проект организован так, чтобы два разработчика могли почти бесшовно переключаться между Windows, macOS и разными компьютерами без переноса рабочих папок и без зависимости от сохранности старого чата Codex.

## Быстрый старт

### 1. Клонировать репозиторий

```bash
git clone <REPOSITORY_URL>
cd <REPOSITORY_DIRECTORY>
```

Не переносите проект между устройствами ZIP-архивами, флешками или ручным копированием папки. Для синхронизации используется только Git remote.

### 2. Подготовить локальное окружение

Понадобятся:

- Git;
- Codex;
- `uv` / `uvx` — для WEEEK MCP;
- Docker Desktop — понадобится для приложения и PostgreSQL;
- Node.js и Python — после появления frontend/backend bootstrap.

Проверка `uv`:

```bash
uv --version
uvx --version
```

### 3. Создать локальный `.env`

macOS / Linux:

```bash
cp .env.example .env
```

PowerShell:

```powershell
Copy-Item .env.example .env
```

Добавить локальный токен WEEEK:

```env
WEEEK_API_TOKEN=...
```

`.env` не коммитится в Git.

### 4. Проверить Codex и WEEEK

В проекте уже хранится общий Codex-конфиг:

```text
.codex/config.toml
```

После запуска Codex проверьте MCP:

```text
/mcp
```

WEEEK должен быть доступен. Если WEEEK временно не работает, продолжать работу всё равно можно по Git и task handoff.

### 5. Восстановить контекст проекта

В новой Codex-сессии:

```text
$project-resume
```

Codex должен самостоятельно определить текущую ветку, прочитать `AGENTS.md`, состояние проекта, task handoff, Git diff и при возможности WEEEK-задачу.

Не нужно пересказывать старый чат.

Сейчас подготовлен документальный и организационный каркас проекта.

```text

Frontend   → Vite dev server
```

Актуальное состояние всегда смотреть в [`docs/current-state.md`](docs/current-state.md).

## Как начать рабочий день

Сначала синхронизировать Git:

```bash
git fetch --all --prune
git status
git branch --show-current
```

Если начинаете с `main`:

```bash
git switch main
git pull --ff-only
```

Если продолжаете существующую задачу:

```bash
git switch feature/UT112-123-short-slug
git pull --ff-only
```

После этого в Codex:

```text
$project-resume
```

## Как взять новую задачу

### 1. Выбрать задачу в WEEEK

Нормальный поток:

```text
Backlog
  ↓
Ready
  ↓
In Progress
  ↓
Review
  ↓
QA
  ↓
Done
```

Разработчик обычно работает до `Review`. `Done` подтверждается человеком и не выставляется агентом автоматически.

Перед началом убедитесь, что задача свободна, назначьте себя исполнителем, переведите её в `In Progress`, прочитайте acceptance criteria и зависимости.

### 2. Обновить `main`

```bash
git switch main
git pull --ff-only
```

### 3. Создать отдельную ветку

Примеры:

```bash
git switch -c feature/UT112-123-virtual-response-unit
git switch -c fix/UT112-124-incident-status
git switch -c docs/UT112-125-update-domain
```

Одна WEEEK-задача = одна ветка.

Два разработчика не должны одновременно работать в одной feature-ветке без явной договорённости.

### 4. Создать task handoff

Скопировать:

```text
tasks/TEMPLATE.md
```

в:

```text
tasks/UT112-123.md
```

Заполнить минимум:

```text
Goal
Acceptance criteria
Owner
Branch
WEEEK
Exact next step
```

Task handoff — это техническая память **конкретной задачи**.

### 5. Начать работу

Запустить:

```text
$project-resume
```

Codex должен восстановить контекст уже из новой ветки и handoff-файла.

## Если Codex завис или потерял контекст

Не тратьте много времени на спасение длинной сессии.

Если полезные изменения уже находятся в рабочей папке:

```bash
git status
git diff
```

Откройте новую сессию и выполните:

```text
$project-resume
```

Новый агент должен восстановить состояние из:

```text
Git branch
+ git diff
+ recent commits
+ tasks/UT112-xxx.md
+ project docs
+ WEEEK
```

Если предыдущая сессия ещё работает достаточно, чтобы сохранить состояние, сначала используйте:

```text
$project-checkpoint
```

## Что делать перед сменой устройства или паузой

Главное правило:

> Не оставляйте уникальную полезную работу только на одном компьютере.

Перед паузой:

```text
$project-checkpoint
```

Проверьте, что `tasks/UT112-xxx.md` содержит:

```text
что сделано
что сейчас в работе
какие файлы изменены
какие проверки выполнены
есть ли блокеры
один точный следующий шаг
последний commit
отправлен ли он в remote
```

Если задача не закончена, checkpoint-коммит допустим:

Не используйте `git add .` вслепую. `$project-checkpoint` должен добавить только файлы текущей задачи и handoff. При ручном checkpoint сначала проверьте `git status`, затем stage только нужные файлы:

```bash
git status
git add <файлы-текущей-задачи> tasks/UT112-123.md
git commit -m "chore(UT112-123): сохранить промежуточное состояние"
git push
```

В `main` служебная история не попадёт, если PR будет влит через squash merge.

## Git-правила

### Ветки

```text
feature/UT112-xxx-short-slug
fix/UT112-xxx-short-slug
refactor/UT112-xxx-short-slug
test/UT112-xxx-short-slug
docs/UT112-xxx-short-slug
chore/UT112-xxx-short-slug
```

### Коммиты

```text
<type>(UT112-xxx): <описание на русском>
```

Примеры:

```text
feat(UT112-123): добавить назначение группы реагирования
fix(UT112-124): исправить переход статуса карточки
docs(UT112-125): уточнить предметную модель ДДС
```

Основные типы:

```text
feat
fix
refactor
test
docs
chore
build
ci
perf
revert
```

### Pull Request

Название:

```text
[UT112-123] Краткое описание
```

Правила:

```text
никаких прямых push в main
одна задача = одна ветка = один PR
merge через Pull Request
предпочтительно squash merge
```

## Перед Pull Request

Минимально необходимо:

1. выполнить проверки, относящиеся к задаче;
2. проверить `git diff`;
3. убрать временный код, `print` и `console.log`;
4. обновить `tasks/UT112-xxx.md`;
5. обновить документацию, если изменилось поведение;
6. сверить результат с acceptance criteria;
7. отправить все изменения в remote;
8. перевести задачу в `Review`.

После появления backend/frontend конкретные команды проверок будут добавлены сюда.

Ожидаемый набор:

```bash
pytest
ruff check .
npm test
npm run lint
```

E2E для критических сценариев — Playwright.

```text

                       │

                       │
┌──────────────────────▼───────────────────────┐

└──────────────────────┬───────────────────────┘

```

Важное решение, которое существует только в чате, считается **не сохранённым**.

## Предметная модель в двух словах

Основной обучаемый:

```text
Диспетчер ДДС
```

Базовый поток:

```text
Virtual112
    ↓
готовая карточка происшествия
    ↓
диспетчер ДДС
    ↓
Принята / Не принята
    ↓
назначение группы реагирования
    ↓
виртуальная группа реагирования
    ↓
сообщения о ходе работ
    ↓
обучаемый самостоятельно меняет статусы карточки
    ↓
Assessment
```

Для MVP группа реагирования виртуальная, а телефонный обмен временно имитируется встроенным онлайн-чатом.

**Состояние виртуальной группы не меняет статус карточки автоматически.** Интерпретация сообщения и выбор правильного статуса — часть задания обучаемого.

Подробнее: [`docs/domain.md`](docs/domain.md)


## Секреты и материалы заказчика

Не коммитить:

```text
.env
API tokens
пароли
секреты
материалы заказчика с ограниченным доступом
```

Для материалов заказчика используется отдельный skill:

```text
$customer-materials
```

В контекст нужно загружать только документы, относящиеся к текущей задаче.

Каталог `materials/customer/` намеренно не синхронизируется через Git. Поэтому обычное продолжение разработки на другом устройстве работает по репозиторию, но для повторной проверки первоисточников материалы заказчика должны быть отдельно доступны на этом устройстве через согласованное приватное хранилище.

## Если сомневаетесь, что делать дальше

1. Проверьте текущую ветку:

```bash
git branch --show-current
```

2. Запустите:

```text
$project-resume
```

3. Посмотрите `docs/current-state.md` и `tasks/UT112-xxx.md`.

4. Если это новая работа — выберите `Ready`-задачу в WEEEK и создайте отдельную ветку.

5. Если появилось новое долговременное решение — сохраните его в документации, а не только в чате.
