# Учебный тренажер 112

## Первичный запуск проекта

Клонируйте репозиторий, создайте чистую PostgreSQL-базу и настройте `DATABASE_URL` в `.env` по образцу `.env.example`. Затем из каталога `backend` выполните:

```bash
uv sync
uv run python -m app.scripts.bootstrap_demo
```

Команда применяет Alembic, импортирует версионированные CORE/DEMO данные и проверяет реальные количества записей. Подробности: [воспроизводимые данные PostgreSQL](docs/database-seeding.md).

Тренажер для подготовки диспетчеров ДДС к работе с карточками происшествий Системы-112.

## Локальный запуск приложения

Требования: Python 3.12+, [uv](https://docs.astral.sh/uv/), Node.js 22+ и PostgreSQL 16+.

Перед запуском создайте локальную базу `training_simulator_112`, скопируйте `.env.example` в `.env` и при необходимости измените `DATABASE_URL`.

После клонирования приложение запускается из корня репозитория одной командой:

macOS / Linux:

```bash
python3 dev.py
```

Windows:

```powershell
py dev.py
```

При первом запуске скрипт сам установит отсутствующие зависимости. Перед запуском сервисов он выполняет `alembic upgrade head` для базы из `DATABASE_URL`; при ошибке миграции сервисы не запускаются. По умолчанию backend доступен на `http://127.0.0.1:8000`, frontend — на `http://127.0.0.1:5173`. Для остановки обоих процессов нажмите `Ctrl+C`.

## Запуск в учебном классе по локальной сети

На компьютере сервера определите его адрес в LAN, например `192.168.1.25`. В корневом `.env` задайте:

```env
BACKEND_HOST=0.0.0.0
FRONTEND_HOST=0.0.0.0
BACKEND_PORT=8000
FRONTEND_PORT=5173
VITE_API_URL=http://192.168.1.25:8000
FRONTEND_ORIGINS=http://192.168.1.25:5173
```

Запустите `python3 dev.py` (Windows: `py dev.py`). С другого компьютера откройте `http://192.168.1.25:5173`. API и Socket.IO работают на `http://192.168.1.25:8000`. Замените адрес на фактический IP сервера и откройте порты в локальном файрволе. `0.0.0.0` — только bind-адрес, а не адрес браузера. После изменения `VITE_API_URL` перезапустите Vite.

Backend проверяет подключение к PostgreSQL при старте и завершает запуск с ошибкой, если база недоступна.

После запуска занятия преподаватель открывает его из списка и видит live-монитор класса. Монитор восстанавливает состояние через `GET /api/training/sessions/{id}/monitor`; read-only состояние конкретного АРМ доступно через `GET /api/training/sessions/{id}/runs/{run_id}/workstation`. Socket.IO сообщает об изменениях, а браузер повторно запрашивает REST snapshot; для online/offline используется heartbeat обучаемого.

При необходимости сервисы можно по-прежнему запускать отдельно. Backend:

```bash
cd backend
uv sync
uv run uvicorn app.main:socket_app --reload
```

API будет доступен на `http://localhost:8000`, проверка состояния — `GET /health`, интерактивная документация — `/docs`.

Локальный стенд создаёт миграцией три demo-пользователя: администратора, преподавателя и обучаемого. Текущий пользователь доступен через `GET /api/users/me`; по умолчанию выбран обучаемый, а для переключения frontend передаёт имя в заголовке `X-Demo-User`. Это только механизм локальной демонстрации, не промышленная аутентификация.

Кабинет преподавателя открывается при выборе demo-пользователя с ролью `INSTRUCTOR`. В разделе «Занятия» преподаватель создаёт черновик, задаёт режим, длительность, интервал и порядок выдачи, видит подключённые АРМ, массово назначает профиль ДДС, сложность, группу и тип очереди. Группы можно менять до запуска; настройки и состав фиксируются после запуска. Экран готовности предупреждает об offline-участниках, но не блокирует из-за них старт. Шаблоны сохраняют настройки без привязки к обучаемым. На шаге «Задания» преподаватель формирует, проверяет, изменяет, заменяет и утверждает пул карточек. FLOW выдаёт подготовленные карточки каждому АРМ по серверному расписанию; FIXED_SET требует утверждённую карточку для каждой очереди и выдаёт набор при старте; MANUAL не выдаёт автоматически. Общая очередь и атомарный claim реализованы. Socket.IO уведомляет об изменениях, а frontend перечитывает REST после уведомления или reconnect.

API занятий расположен по адресу `/api/training/sessions`. Обучаемый занимает свободное АРМ командой `POST /{id}/join` с `workstation_number`; номер хранится в `TrainingRun`, а не в `User`. `POST /{id}/heartbeat` обновляет online-индикатор и отвечает `204`, не отдавая полный пул. Список занятий для обучаемого содержит краткую сводку и собственный run; преподавательский setup получает полное состояние. Преподаватель переводит подготовленный черновик в `READY` командой `POST /{id}/prepare` и запускает командой `POST /{id}/start`. Запуск требует подключённых участников и назначенного каждому профиля ДДС. Время запуска формирует backend.

Готовые карточки происшествий доступны через `/api/incidents`. В активную учебную сессию преподаватель доставляет карточку командой `POST /api/incidents`; backend копирует исходные данные сценария в неизменяемый snapshot и сам фиксирует `created_at` и `delivered_at`. Обучаемый, назначенный на сессию, получает реестр через `GET /api/incidents`, открывает карточку командой `POST /api/incidents/{id}/open` и восстанавливает её через `GET /api/incidents/{id}`. Первое открытие идемпотентно фиксируется backend в `opened_at`; клиент это время не вычисляет.

Статус реагирования ДДС изменяется командой `POST /api/incidents/{id}/actions` только после `POST /open`. Backend возвращает `available_actions`, проверяет роль, назначение, обязательные комментарии и терминальные состояния, а также хранит неизменяемую историю `IncidentAction` с серверным временем и снимком имени исполнителя. Завершение работ или отказ от них переводят lifecycle в `FINISHED`. Доставка и первое открытие создают в той же истории системные события `SERVICE_ADDED` и `SERVICE_RECEIVED`. Норматив первичного решения вычисляется как `primary_status_at - delivered_at` и доступен в API в секундах.

`TrainingRun` создаётся при подключении обучаемого к АРМ и содержит его настройки на всё занятие. Новую карточку преподаватель может адресовать конкретному участнику через `trainee_id` в `POST /api/incidents`; при единственном участнике он определяется автоматически. `training_run_id` возвращается в карточке. Если участников несколько, `trainee_id` обязателен. Карточки, созданные до этой миграции для многопользовательской сессии, сохраняют прежний доступ, но виртуальную группу на них назначить нельзя без однозначной принадлежности.

Виртуальные группы хранятся отдельно от своих назначений. Преподаватель создаёт справочную группу через `POST /api/response/units` с полями `name`, `dds_profile`, `description`; обучаемый получает подходящие группы через `GET /api/response/units?incident_id={id}` и назначает одну через `POST /api/response/incidents/{id}/assignments`. Назначение разрешено после принятия карточки и сохраняет собственное состояние и историю. `GET /api/response/incidents/{id}/assignments` восстанавливает их после перезагрузки. Для первого MVP профиль участия — `ДДС`; группы с другим `dds_profile` не предлагаются этому обучаемому.

Сценарный механизм применяет последовательные события к назначению через `POST /api/response/assignments/{id}/scenario-events` от преподавателя. Тело содержит уникальный `event_key` и `target_state`. Повтор ключа идемпотентен; время фиксирует сервер. API допускает `ASSIGNED → ACKNOWLEDGED → EN_ROUTE → ARRIVED → WORKING → COMPLETED` и отмену из незавершённого состояния. Планировщик выпускает подготовленные события и сообщения; встроенный чат хранит историю в БД. Состояние группы не меняет статус ДДС автоматически.

```bash
cd frontend
```

Стартовый экран будет доступен на `http://localhost:5173`.

Smoke E2E на отдельной тестовой PostgreSQL-базе: примените миграции, добавьте второго demo-обучаемого командой `E2E_SEED=1 uv run python -m tests.e2e_seed` в `backend`, запустите приложение с `DATABASE_URL` этой базы и выполните `npm run test:e2e` в `frontend`, явно задав `E2E_BASE_URL` и `E2E_API_URL` для этого стенда. Без обоих адресов E2E не запускается. Сценарии проверяют путь обучаемого, общий claim и подготовку занятия преподавателем. Реальный concurrency-тест PostgreSQL запускается с `RUN_POSTGRES_TESTS=1 uv run pytest -q tests/test_postgres_claim.py` на той же изолированной базе. Эти тесты не предназначены для рабочей базы.

CI выполняет Ruff, pytest, frontend lint и build. Владелец репозитория может включить protection для `main` с обязательными проверками после проверки workflow; политика репозитория автоматически не меняется.

Перед первым запуском скопируйте `.env.example` в `.env`. Реальные токены и локальный `.env` не добавляются в Git.

Проект делают **два разработчика** на нескольких компьютерах. Поэтому процесс специально сделан простым:

> **WEEEK говорит, что делать. Git хранит работу. Codex помогает продолжить с того же места.**

В WEEEK всего три колонки:


# Первый запуск на компьютере

## 1. Клонировать проект

```bash
git clone <REPOSITORY_URL>
cd <PROJECT_FOLDER>
```

Рабочую папку между Windows и Mac вручную не переносим.

## 2. Подготовить `.env`

Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

macOS / Linux:

```bash
cp .env.example .env
```

Указать локальный токен WEEEK:

```env
WEEEK_API_TOKEN=...
```

`.env` в Git не добавляется.

## 3. Проверить WEEEK в Codex

Для WEEEK MCP нужен `uv` / `uvx`.

```bash
uv --version
uvx --version
```

В Codex:

```text
/mcp
```

Если WEEEK подключён — отлично. Если нет, работа с Git всё равно возможна.

# Как начать новую задачу

## В WEEEK

Выбери свободную задачу в колонке:

```text
К работе
```

После этого просто скажи Codex:

```text
Начни задачу UT112-12
```

Codex должен сам:

- прочитать WEEEK-задачу;
- назначить тебя исполнителем;
- перевести её в `В работе`;
- проверить текущую Git-ветку;
- **обязательно создать или выбрать отдельную ветку с ID задачи**;
- повторно проверить имя текущей ветки;
- только после этого подготовить handoff и менять файлы;
- прочитать нужную документацию;
- начать реализацию.

Если Codex остался на `main`, start workflow считается неуспешным — файлы задачи менять нельзя.

Руками создавать handoff обычно не нужно.

# Как работать дальше

Обычная работа — обычный диалог с Codex.

Например:

```text
Добавь обработку статуса «Принята».
Сделай экран карточки ближе к референсу.
Добавь тесты.
Исправь ошибку.
```

Не нужно каждый раз запускать специальный skill вручную.

---

# Как перейти на другой компьютер

На первом компьютере скажи:

```text
Сохрани состояние, продолжу на другом компьютере
```

Codex должен обновить handoff, сделать commit и push.

На втором компьютере:

```bash
git fetch --all --prune
git pull
```

Если нужная ветка ещё не выбрана:

```bash
git branch -a
git switch <branch-name>
git pull
```

После этого в новой сессии Codex:

```text
Продолжи текущую задачу
```

Старый чат для этого не нужен.

---

# Если Codex завис

Открой новую сессию в той же рабочей папке и напиши:

```text
Продолжи текущую задачу
```

Codex восстановит состояние из Git, handoff и WEEEK.

Если предыдущая сессия ещё отвечает, лучше сначала сказать:

```text
Сохрани состояние
```

---

# Как закончить задачу

Скажи:

```text
Задача готова, проверь всё
```

Codex должен:

- свериться с задачей;
- запустить проверки;
- проверить diff;
- убрать временный код;
- обновить handoff;
- commit/push изменений.

Потом вы вручную проверяете результат.

Если всё нормально:

```text
Всё работает, заверши задачу
```

После этого Codex может перевести WEEEK-задачу:

```text
В работе → Готово
```

# Git — кратко

Одна задача = одна ветка.

Примеры:

```text
feature/UT112-12-virtual-response-unit
fix/UT112-13-incident-status
docs/UT112-14-domain-update
```

Прямо в `main` не работаем.

Переключение устройств:

```text
commit → push → pull
```

Не переносим проект ZIP-архивом или флешкой.

## Инструкция товарищу в 20 секунд

1. Возьми свободную задачу в WEEEK.
2. Скажи Codex: **«Начни задачу UT112-XX»**.
3. Работай.
4. Перед уходом: **«Сохрани состояние, продолжу на другом компьютере»**.
5. На другом компьютере сделай `git pull` и скажи: **«Продолжи текущую задачу»**.
6. Когда всё готово: **«Задача готова, проверь всё»**.
